## 1. Calling conventions (`[FFI-9]`)

Helper B built `unsafe extern "system" | "fastcall" | "vectorcall"` declaration blocks. Now an
Ember function is *defined* in any of the four conventions (`pub extern "system" fn f()`), and a
function pointer type names one (`extern "fastcall" fn(i32) -> i32`). The convention is part of the
pointer's type: a `"system"` function is not an `extern "C" fn` (E2020, they differ on 32-bit
Windows). `"C++"` is E0900 (Annex C); any other string is E0104, as for blocks
(`check_calling_convention` in `ember_typeck`). The C definition and prototype carry the
`EMBER_CC_*` macro B defined; the package header defines the macros when an export or a pointer
type in it needs one.

Every place that meant "a C-ABI definition" by testing `abi == Some("C")` now tests `abi.is_some()`
(export wrappers' thread attach and contract, `@export` retention, the header's exports, reload's
export flags, symbol-collision checks).

**Decision:** a value with drop glue in an `extern` function pointer's signature (was E0900, "until
ABI lowering") is `E5015`: such a pointer is a boundary C can call through, and C cannot run an
Ember `drop`, which is exactly `[FFI-31b]` (`E5015`, "type may not cross the boundary"). Nothing
remained to lower.

Tests: `tests/conformance/FFI-9/accept_definitions_and_pointers_in_each_convention.em`,
`reject_a_pointer_of_another_convention.em`, `reject_a_drop_bearing_value_through_a_foreign_pointer.em`.

## 2. The runtime as a host embeds it (`[FFI-27]`)

* **Logging.** What the runtime says on its own account — the debug leak report, the note that no
  report was made because threads still run, the leak-metadata allocation failure — goes to the
  config's `log(level, msg, len)` when the host gives one, else to standard error. The leak report
  is one message (`EMBER_RT_LOG_WARNING`): its printing was rewritten from `FILE*` to a small
  `rt_text` writer that either writes to a file or gathers the text (`rt_textf`). Panics keep going to
  `on_panic`. `EMBER_RT_LOG_ERROR/WARNING/INFO` are in `ember_rt.h`.
* **At-exit hooks.** `int ember_rt_at_exit(void (*hook)(void*), void* data)`; `ember_rt_shutdown`
  runs them newest first, each once, before the leak report, and forgets them (a hook registered by
  a hook runs too).
* The ABI version was not bumped: these are additions; a caller of the old surface links unchanged.

Test: `ember_build` `a_host_routes_logging_and_shutdown_runs_at_exit_hooks`
(`runtime/ember_rt/templates/tests/embedding.c.in`): host allocation and log functions, two hooks
in order, the leak report reaching the log and not stderr.

## 3. Shared libraries (`[FFI-28]`, `[FFI-31]`, `[FFI-31a]`, `[FFI-31c]`, `[ABI-3]`)

`kind = "cdylib"` builds `target/<profile>/lib/<name>.dll` (`lib<name>.so`), its import library on
Windows, `<name>.h`, and the runtime header beside it (`ember_build/src/cdylib.rs`,
`link_cdylib`).

* **Exports only the exports.** What is exported is a list, not annotations in the C: a
  module-definition file on Windows, a version script elsewhere (`local: *`), which also keeps the
  private runtime's symbols inside. `-Bsymbolic` binds the library's calls of its own exports to
  itself, so a host that loads two Ember libraries never sends one's call into the other.
* **Entry points** (generated by `emit_module_entry`): `int ember_module_init(const ember_rt_config*)`
  first compares `ember_rt_abi_version()` with the `EMBER_RUNTIME_ABI` it was compiled against and
  returns `EMBER_MODULE_INIT_ABI_MISMATCH` (4, distinct from `ember_rt_init`'s 3) before anything
  else (`[ABI-3]`); then it copies the host's config (no field past its `size`), turns the debug
  object registry on in `debug` (the leak report), initialises the module in its runtime, registers
  the debug edge enumerators and records its **creator** thread. A second call while initialised
  changes nothing. `ember_module_shutdown` runs the runtime's shutdown when this is its last module.
* **Modules are counted by the runtime** (`ember_rt_module_init_v2`/`ember_rt_module_shutdown`): the
  first initialises it, the last shuts it down unless the host initialised it itself
  (`ember_rt_init`), which then owns its shutdown.
* **Thread contract per module** (`[FFI-33]`): a `cdylib`'s `main`/`creator` exports check
  `ember_rt_check_module_thread(creator)` against the module's own creator (a static in the
  library), not the runtime's first initialiser, so it is per module even in a shared runtime; a
  call before `ember_module_init` or after shutdown panics.
* **Shutdown** (`[FFI-31]`): at-exit hooks, the leak report in `debug` (to the host's log when it
  has one), every thread detached by the epoch moving on (`[FFI-31a]`: no TLS destructor exists
  anywhere in the runtime, which the test checks), and — new — the job workers the module started
  are stopped and joined (`jobs_stop`), so none runs the library's code after the host unloads it.
  A program's own exit still does not wait for its workers (`[THR-16]`). A thread's state is
  thread-local storage, freed with the thread or the library; the one heap block a thread can own
  (a debug access stack past 16 entries) is freed when its last access ends.
* **`[build] runtime = "shared"`** (`[FFI-31c]`): the library imports the process's one shared
  runtime, A's `shared_runtime` built **without** the reload definitions
  (`shared_runtime(..., reload: Option<bool>, ...)`, `None` here), placed in `lib/` beside the
  libraries; a library finds it through `$ORIGIN` off Windows. `[FFI-31b]`'s E5015 applies to every
  export as before.
* A library with a `@fastmath` function is refused like a static library's (E0900).

Tests (`compiler/ember_driver/tests/cdylib.rs`): `a_cdylib_is_loaded_initialised_and_unloaded_by_a_c_host`
(exact export set from the PE export table / `nm -D`, entry points, two threads, leak report to the
log, unload with an attached thread still alive, reload, `main` export before init and on another
thread), `shared_libraries_share_one_runtime` (one runtime loaded, the host's at-exit hook runs at
the last module's shutdown only, E5015 on an owning export), `a_module_built_for_another_runtime_abi_is_refused_first`
(the module's C compiled against the next ABI's header), `shutdown_ends_the_job_workers_a_module_started`
(thread count back to its start; fails without `jobs_stop`, 27 threads left).

## 4. `@export_table`, exact symbols, generic exports (`[FFI-26]`, `[FFI-33c]`, `[MNG-2]`)

* `@export_table("Name", protocol=N)` on a struct whose fields are `extern` function pointers:
  **each field holds the function of its own name**, which must have exactly the field's type
  (E2020 otherwise; E1010 when there is none; a field that is not a function pointer is E0104). The
  binding by name follows the specification's own examples (the 0.5/0.8 `ScriptApi` with fields
  named like the module's functions); see question Q3. Typeck records `ember_types::ExportTable`s
  in the type table; the C is `const <struct> Name = { f1, f2 };` and
  `const uint32_t Name_protocol_N = N;` — the protocol is a symbol whose name carries the number
  (`[ABI-1]`'s "a linked symbol whose name encodes the number"), so a host built for another protocol
  does not find it. The header declares both, `#define Name_PROTOCOL N`, and each entry's thread
  contract. A `cdylib` exports both (as data), an executable keeps them under `--gc-sections`.
* `[FFI-33c]` per field: an entry's contract is its function's (`@export(threads=…)` on it, else the
  file's `#! threads`), so a table sets `threads` field by field with the existing attribute; the
  `main` entry panics on another thread in every profile (the test builds debug, release and
  shipping).
* `[MNG-2]` "`@export("name")` sets the symbol exactly", also for a symbol C cannot spell
  (`@export("game-update")`, was E0900): the function's C name is `em_0x` and the symbol's bytes in
  hex (`ember_branding::export_alias`; no mangled name has a digit after `em_`), and its object-file
  symbol is set by an assembler label (`__asm__`, after `__USER_LABEL_PREFIX__`; quoted for GNU as,
  since GCC writes the label as it is) or, with MSVC, `/ALTERNATENAME:exact=alias`; a `cdylib`'s
  module-definition file exports it as `exact=alias`. A symbol holding a space, quote, backslash or
  control character cannot be a linker symbol (E0104).
* A generic `@export` is **E2060** ("its type parameters cannot be inferred for one C symbol"), not
  E0900: a C symbol names one function, and an export has nothing to infer the parameters from —
  E2060's meaning (`cannot infer type`).

Tests: `tests/conformance/FFI-26/accept_an_export_table.em` (the program reads its own table back
through foreign statics), `reject_an_export_table_field_without_its_function.em`,
`accept_an_export_symbol_that_is_not_a_c_identifier.em`, `reject_unsupported_export_forms.em`
(rewritten); cdylib tests `an_export_table_is_found_by_name_with_threads_per_entry` and the
`plugin-odd` export in the flow test.

## 5. `[link] libs` (`[BLD-FFI-3]`)

`[link] libs = ["shlwapi", "vendor/libfoo.a"]`: a name is searched for by the toolchain
(`name.lib`, `-lname`), a path (anything with a directory or a library extension) is relative to
the manifest. Linked after the program's objects, in the order written, for programs and
`cdylib`s. A program linking libraries skips the program cache (its key would need the libraries'
contents) and, with MSVC in `debug`, links with `/INCREMENTAL:NO`: **found defect** — an
incremental link kept the symbol it had resolved before, so swapping two libraries did not change
which one defined `which_lib` (the test caught it). Test: cdylib.rs
`libraries_link_by_path_and_name_in_declaration_order`. The `link = [...]` of an `import c` waits on
the importer (unfinished entry).

## 6. The toolchain (`[TOOL-4]`, `[VER-2]`)

* `ember --version` prints the compiler version, `language: 0.9.10`, `backend: c`, the C compiler
  it resolves (as a build would: `EMBER_CC`, else detection) with its path, and the linker
  (`link.exe` beside `cl.exe`; GCC's and Clang's own `-print-prog-name=ld`). `--json` gives the same.
  `--version --matrix` was silently ignored; it is now E0900 (`[CLI-19]`).
* `ember new <name> [--bin | --lib | --cdylib]`: the manifest (`name`, `version = "0.1.0"`,

* `ember run`, `build` and `check` with no file find the package's manifest above the current
  directory and use its entry.
* `[package] language` names the language a package opts into; before 1.0 only the current one
  (E9001 otherwise, naming it; `[VER-8]`). `[package] version` must be `MAJOR.MINOR.PATCH` (E9001).

## 7. Packages (`[MOD-1]`, `[MOD-2]`, `[MOD-4]`, `[MAN-2]`, `[VER-5]`)

`compiler/ember_driver/src/packages.rs`.

* **Dependencies**: `name = { path = "…" }` (relative to the manifest naming it), `[dependencies.name]`
  tables, and `name = { git = "…", rev = "…" }`, cloned once into the build cache and checked out at
  the revision. The dependency's manifest must name the package the key names. `std = "…"` is
  skipped (implicit). A bare version requirement (`name = "1.2"`) needs a registry the specification
  does not describe: E0900 (question Q1); a malformed one is E9001.
* **Module paths** (`[MOD-1]`): a dependency's modules are its name followed by their path; `import
  geometry.shapes` inside a package resolves the package's own module first, then a dependency of
  that name, then `std`. A package's own name may start a path. The root package keeps its old,
  unprefixed paths; a dependency named like one of the root's own modules is E9001.
* **Two majors coexist** (`[VER-5]`): a package is identified by name and major version. The first
  major reached keeps the bare name; another is `name__<major>`, and the imports inside the packages
  depending on it are rewritten to that path, binding the same name (an alias when the last segment
  changes). So `em_geometry_shapes_Square` and `em_geometry__1_shapes_Square` coexist. Two sources
  of one name and major are E9001, never a silent choice.
* **Visibility** (`[MOD-2]`): `LoadedModule` now carries its package; `pub(package)` holds within one
  package (was: everything outside `std` was one package), and `[BRW-10]`'s field-set borrowing
  treats a dependency's `pub` methods as seen by its dependants.
* **Cycles** between packages are E1041 (`[MOD-4]`).
* **`ember.lock`** (`[MAN-2]`): each dependency's name, version, source (`path+…`, `git+url#rev`)
  and a blake3 hash of its manifest and every file under `src/` (line ends normalised). A build
  writes it when it would change; `--locked` refuses instead, saying whether there is none or the
  dependencies changed; `ember update` rewrites it; `ember update <name>` takes only that package's
  entries anew and keeps the rest as locked.

Tests (`package.rs`): `two_majors_of_a_dependency_coexist` (E1052 on a dependency's
`pub(package)`), `the_lock_records_dependencies_with_content_hashes`,
`a_git_dependency_is_checked_out_at_its_revision`, `dependency_errors` (E1041, a bad version, the
registry E0900); unit tests in `packages.rs` (semantic versions, `ember update <name>`'s merge).
The `[MAN-8]` every-key milestone now resolves real dependencies and names the current language.

## 8. Layers (`[STD-6]`, `[BLD-11]`)

`[package] layers = ["core", "alloc", …]`. **Decision:** a layer is linked by what needs it, and that
is an effect the compiler already computes over the call graph (`[EFF-1]`): `alloc` by `Alloc`;
`sync` by `Sync`, `Lock` and `Block`; `io` by `Io`; `ffi` by `FFI`; `core` by nothing. A function of
a package whose effects need a layer it leaves out is **E1021** ("`f` needs the `alloc` layer,
which is not linked in this build"), at the first operation on the way, with the chain
(`ember_analysis::effects::check_layers_all`). This makes the layers of `std` follow from its items
rather than from a hand-kept list per item — `std.collections` holds both `Array` (alloc) and
fixed-capacity containers (core), so no per-module list could be right — and "each layer depends
only on the ones before it" holds by construction. A layer listed without the ones before it
(`["core", "io"]`) is E9001; a package that leaves out a layer cannot depend on a package declaring
it (E1021, at resolution). No `layers` key means every layer. Error page `docs/errors/E1021.md`.

Known limit (not a question): `[STD-6]` puts *time* and *processes* in `io`, but `[EFF-1]`'s `Io` is
file, socket and console operations: `std.process.args` (the one such function today) carries only
`Alloc`, so a `["core", "alloc"]` package may call it. `std.time`/`std.process` do not exist yet;
when they are written, their clock and process functions should carry `Io` or this check will not
see them.

Test: `package.rs` `a_package_uses_only_its_layers`.

## 11. Owner questions (each a real choice or a contradiction)

**Q1 — where does a version requirement resolve from?** `[MAN-8]`: "`[dependencies]` (a version
requirement, `{ path }`, or `{ git, rev }`)"; `[VER-5]`: "a requirement `"1.2"` means `>= 1.2.0,
< 2.0.0`; resolution picks the highest version satisfying every requirement". Nothing names where
the candidate versions come from. Options: (a) a package registry with an index (a URL in the
manifest or a default one; Cargo's model), e.g. `geometry = "1.2"` fetched from
`https://packages.ember-lang.org`; (b) the versions are a git repository's tags,
`geometry = { git = "…", version = "1.2" }` (Go's model; needs a `version` key `[MAN-8]` does not
list); (c) a local directory of packages (`EMBER_REGISTRY=/path`, `<name>/<version>/`), for offline
and company mirrors. Built meanwhile: `name = "1.2"` is E0900, everything else of packages works.

**Q2 — `[build] global_allocator` and `[MAN-8]`'s key list.** `[ALC-3]`: "A binary package may
replace the global allocator with `[build] global_allocator = "module.NAME"`". `[MAN-8]` lists the
`[build]` keys as `entry`, `target`, `backend`, `c_compiler`, `runtime`, `max_instantiations`,
`reload`, and "a key a section does not take … is `E9001`". Today `global_allocator` is E9001. Is
`[MAN-8]`'s list missing it (add it), or is the key meant to live elsewhere? Nothing else is built
for `[ALC-3]` (it needs the `Allocator` interface).

**Q3 — `@export_table`'s shape.** `[FFI-26]`: "`@export_table("Name", protocol=N)` on a struct of
`extern "C" fn` fields exports a table of function pointers under that name and protocol version";
`[FFI-33c]`: "An `@export_table` may set `threads` per field"; `[ABI-1]` lists "the export-table
protocol" among the versions that are "a linked symbol whose name encodes the number". Built: each
field holds the module's function of the field's name (as in the 0.5/0.8 examples); the protocol is
the symbol `Name_protocol_N`; a field's `threads` is its function's own `@export(threads=…)`.
Alternatives: (a) fields name their functions explicitly with defaults
(`on_update: extern "C" fn(u64, f32) -> i32 = update`), letting one function fill two tables or a
field differ from its function's name; (b) the protocol number in the table's own symbol
(`RvScriptApi_v3`) instead of a second symbol; (c) `threads` on the field itself
(`@export(threads=main) on_draw: …`), which `[ATT-1]`'s table does not admit on a field today.

**Q4 — the module protocol's linked symbol (`[ABI-1]` against `[FFI-28]`).** `[ABI-1]`: "the module
protocol … each version is a linked symbol whose name encodes the number, so a mismatch fails at
link time". `[FFI-28]`: a `cdylib` is "a shared library exporting only its `@export` symbols plus
`ember_module_init` and `ember_module_shutdown`" — names without a number, and no room for another
symbol. Options: (a) add a versioned symbol (`ember_module_protocol_v1`) to `[FFI-28]`'s list; (b)
version the two entry points' names (`ember_module_init_v1`), changing `[FFI-28]`; (c) the module
protocol is versioned only through the runtime ABI check `ember_module_init` already makes. Built:
(c) — nothing extra is exported.

## 12. Defects found

* **Fixed — stale incremental link** (MSVC, `debug`): a program linked with libraries kept the
  symbol resolution of its previous link when only the libraries' order changed. Probe/test:
  `libraries_link_by_path_and_name_in_declaration_order` (printed `1` twice). Fix: `/INCREMENTAL:NO`
  when libraries are linked.
* **Fixed — `ember --version --matrix`** printed the version and ignored `--matrix` (`[CLI-19]`,
  `[PHIL-12]`): now E0900.
* **Fixed — a shared library's job workers outlived its shutdown** (they would run unloaded code):
  `shutdown_ends_the_job_workers_a_module_started` (27 threads left before the fix).
* **Open, limits recorded in the code**: a module names no backtrace frames (the runtime keeps one
  table, which a module sharing the runtime would leave dangling when it unloads); in a shared
  runtime, a module that unloads while objects of its types are still alive leaves the debug leak
  report types to name in unloaded code (a leak of the module's own); a `thread.spawn` thread a
  module detached keeps running its code after an unload (as in any C library); on Windows a
  `cdylib` cannot export a symbol holding `=`, `@` or `,` (module-definition syntax); with MSVC a
  static library's exact `@export` symbol is a linker alias that a consumer finds only once the
  library's object is linked in.
