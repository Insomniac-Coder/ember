# M2: weak counts on `weakref` links, and the walk across a call that may change nodes

Measurement job M2 for spec 0.9.15_Hardened_1. Two cost rows of `tasks/96/redesign/run4/v5/rules.md`
section 2 were "not measured"; this job writes the programs that measure them. Nothing here was run
(the brief forbids it): every program was compiled with clang -O2 or rustc, and every C file also
passed MSVC's syntax check (`cl /Zs /W3`, no warnings). The lead runs the timings.

Files (all in `tasks/96/redesign/measure-0.9.15/M2/`):
- `build.txt`: every build line; binaries go to `target/measure-0.9.15/M2/bin/`, already built there.
- `runs.txt`: every binary, its arguments (none), its expected checksum.
- `harness.h`, `rharness.rs`: copied unchanged (the C harness; run 3's Rust port of it).
- `m2_rt.h`: the shared runtime pieces and the one class both workloads use, `Node`.
- workload "tree": `plain_tree.c`, `model_tree.c`, `salvage_tree_parentfree.c`, `rust_tree_rc.rs`,
  `rust_tree_arena.rs`.
- workload "w2v": `plain_w2v.c`, `model_w2v.c`, `salvage_w2v_freeonly.c`, `salvage_w2v_dispatch.c`,
  `salvage_w2v_hoist.c`, `rust_w2v.rs`, `rust_w2v_rc.rs`.
- The assembly the per-step lists below come from: `target/measure-0.9.15/M2/asm/*.s` (clang -O2 -S).

Words: "the C backend" here means the C a compiler would write, built with clang (the lead also builds
with MSVC). "Header test" means one load of the object's count and a compare with 0 (`[WK-12]`;
`[WK-2]`: an object is ended when its count reaches 0).

## The model's layout, shared by both workloads (`m2_rt.h`)

- `class Node` with `value: i32`, `parent: weakref Node = None`, `children: Array[Node] = []`.
- A `weakref` link may name a Node, so the header is 12 bytes: count, type index, weak count
  (`[OBJ-1]`). Node is `{count, type, weak, value, parent, children{ptr,len,cap}}` = 48 bytes, the size
  run 3's W2 model had, so run 3's memory numbers for that layout carry over.
- The weak count starts at 1 on behalf of all owners (`[OBJ-3]`). Making a link: +1, compared with
  its maximum first ("too many `weakref` links to a `Node` (4,294,967,295)", `[WK-11]`, `[RC-4]`).
  Ending a link or giving it another target: -1, and the block is freed at 0 (this is Rust's `Weak`
  drop: a decrement and a test for zero). The end of an object: count to 0 first (`[WK-3]`), then its
  drop method if any, then its fields in order (`parent`: the link's -1; `children`: each child
  ends), then the owners' -1.
- Objects come from run 3's slab (chunks of 4,096 blocks, then a free list), the runtime allocator
  of `[OBJ-4]`. Arrays are Ember's `{ptr, len, cap}`, growing 4, 8, 16, ...
- Language checks kept as run 3's model kept them, through `KEEP` and checked arithmetic: bounds on
  `nodes[...]`, the floor `%` of a call's result (`[TYP-28]`), `unwrap`, overflow on `+` and `*`
  (`[TYP-8]`). `-DPLAIN` removes them and all model work: plain C in the model's layout ("plain_same").

`[WK-17]` (parent-link reads with no header test) holds in both programs: each line that gives
`parent` a target is followed by a push into a place the target owns alone; the one line that takes
a node out (`swap_remove`) is followed, before the link is read, by a line that gives it another
target (or, in `prune`, the node ends); no children list is handed over whole; one owner each; no
drop method (except the `DROPCLASS` builds, where it fails on purpose); one package. Condition 2: no
line between a view of a node and the read of its link can end a Node. So a parent read is a load and
a test for no link.

## Workload "tree": weak counts on links made, re-targeted and ended

### The question

Rules row: "one add and one subtract of the target's weak count, and before each add one compare with
its maximum | every `weakref` link made, given another target or ended (R11), parent links included".
Run 3 never measured it: its tree workloads kept parent links with no count (`set by`). How much do
the counts cost on code that builds and rebuilds trees with parent links, against plain C parent
pointers, against safe Rust's `Weak::clone`/drop, and against run 3's uncounted parent links?

### The program

Run 3's W2 build (the same tree shape, the same random parent choice, the same index of nodes by
number) turned into rounds. Each of 4 rounds, with N = 1,000,000:
1. build: `n = Node(...)`, `nodes.push(weakref n)`, `if nodes[rand() % i] exists as p:`,
   `n.parent = weakref p`, `p.children.push(n)`;
2. move a quarter of the nodes (`(i + round) % 4 == 0`) to a random earlier node: open the index, read
   the parent link (proved), `index_of`, `swap_remove`, `moved.parent = weakref np`, push;
3. read every node once: `value * len(children)` plus its parent's value (a proved parent read);
4. end the round: `nodes` ends (each index link -1), then `root` (the whole tree ends).

The Ember text is the top comment of `model_tree.c`.

Link work per round in `model_tree` (rule as written; counts derived from the program):

| what | how many per round | each |
|---|---|---|
| index link made, `weakref n` | N | compare with max, +1 |
| parent link made, `n.parent = weakref p` | N - 1 | compare with max, +1 |
| parent link given another target | about N/4 | compare, +1 on the new target, -1 on the old |
| index link ended (`nodes` ends) | N | -1, test for 0 |
| parent link ended (its child ends) | N - 1 | -1, test for 0 |
| owners' share given back (each object ends) | N | -1, test for 0, free the block |
| header test, opening an index link | N - 1 (build) + about N/2 (moves) + N (read) | load, compare |
| parent-link read | about N/4 + N | load, test for no link (proved, no header test) |

### The programs

| binary | source | what it is |
|---|---|---|
| `plain_tree` | `plain_tree.c` | careful C: run 3's plain W2 layout (32-byte nodes in one array allocated once, which is also the index; children arrays of pointers growing 2, 4, 8; plain parent pointers; swap removal). Each round clears the array, builds, moves, reads, frees every children array. |
| `plain_same_tree` | `model_tree.c -DPLAIN` | the model's layout and drop order (48-byte slab objects, Ember arrays, an index array, the recursive end of the tree) with no counts, no tests, no checks |
| `model_tree` | `model_tree.c` | the rule as written: every link counted, parent links included (R11, `[WK-11]`, `[OBJ-3]`) |
| `salvage_tree_parentfree` | `model_tree.c -DPARENT_UNCOUNTED` | parent links proved by `[WK-17]` hold no count; index links still counted (run 3's `set by` cost) |
| `rust_tree_rc` | `rust_tree_rc.rs` | safe Rust as the Rust book writes a tree: `Rc<Node>` in the children lists, `RefCell<Weak<Node>>` parent, `Vec<Weak<Node>>` index; each open is `upgrade()` |
| `rust_tree_arena` | `rust_tree_arena.rs` | safe Rust as Rust programmers usually write it: an arena `Vec<Node>` with u32 indices (run 3's `rust_w2` shape), cleared each round |

All six do the same random sequence (one `h_rand()` per built node, one per moved node, in order) and
print the same checksum.

### Why the comparison is fair

- Same work in all six: the same tree each round, the same moves, the same reads.
- The layouts differ where each language's idiom differs, and a same-layout twin isolates that:
  `plain_same_tree` against `plain_tree` is the price of the layout (48-byte objects in their own
  blocks, a separate index, a recursive end of the tree, and the children arrays' growth), and
  `model_tree` against `plain_same_tree` is the price of the rule's run-time work alone.
- `salvage_tree_parentfree` against `model_tree` is exactly the parent links' counts (everything else
  is identical: the same file, one switch).
- Rust's Rc tree does more per open than the model (an `upgrade` is a test plus a count pair; the
  model's open is one test) and pays `RefCell` flags; that is safe Rust's real price for this design,
  and why `rust_tree_arena` is there too.

### What would mean what

- **As fast as C**: `model_tree / plain_same_tree` near 1.0 (the counts hide behind the cache misses
  the build and the end already take), and `model_tree / plain_tree` no worse than safe Rust's best
  (`rust_tree_arena`).
- **Falls short**: `model_tree / plain_same_tree` clearly above `salvage_tree_parentfree /
  plain_same_tree` means the parent links' counts cost something real, and the salvage below decides
  whether the spec should keep them.
- `rust_tree_rc` is the bar for "safe and counted": the model should be under it.

### Salvage: parent links proved by `[WK-17]` hold no weak count (`salvage_tree_parentfree.c`)

The rule as written counts every link, "with no exception" (R11). The salvage: a parent link whose
reads `[WK-17]` condition 1 proves holds no weak count.

Safety argument. A weak count does one thing: it keeps the target's block in memory so that a later
header test can read it. A parent link that `[WK-17]` condition 1 covers is never header-tested: the
proof says that while a node lives its parent owns it, so every read finds a live target and is
compiled as a plain load. Who else could read the target's block through this link?
- A read during a drop chain (the parent ended, its children ending): condition 1 requires a class with
  no drop method, so no program code runs during the chain, and the field drops do not read the link.
- A node taken out of its place: condition 1 requires the link to be re-targeted or cleared before it
  is read; re-targeting an uncounted link changes no count either.
- Another link made from it (`a = weakref n.parent`): a new link, which takes its own count as usual.
- The link handed over out of the object (moving the field's value into a local): the compiler sees
  the hand-over and adds the count there; a link that leaves the proof takes a count.
So with or without the count the program reads the same memory at the same moments, and the count
moves numbers that no test uses. It costs one store per link change, run 3's `set by` link (D7),
reached from R11's own proof instead of a separate word. If the timings show the counts are near
free, the rule stays as written and this salvage is not needed.

Two ideas that do not help (not built): batching the N subtracts when `nodes` ends gains nothing, each
is one read-modify-write on a different object; and the compare before each +1 cannot be proven away
in general (2^32 links of 8 bytes each is 32 GiB, which a large machine can hold), and Rust's `Rc`
keeps the same compare.

### Memory (the expected peaks, and why)

- `plain_tree`: run 3's plain W2 layout, measured at 54,940 KB for this tree (`run3/26-timer.md` line
  20): 32 MB of nodes plus about half a million children arrays (in a random recursive tree about half
  the nodes are leaves). Rebuilding reuses the node array, so the peak stays near that.
- `plain_same_tree`, `model_tree`, `salvage_tree_parentfree`: run 3's model W2 layout, measured at
  84,368 KB (line 22): 48 MB of 48-byte nodes, the children arrays with Ember's growth from 4, the 8 MB
  index. The slab's free list reuses every block in the next round, so the peak should not grow with
  the rounds. The weak count changes nothing in memory: it sits in the header that was 12 bytes in run
  3 already. The counts never keep a block longer here: the index ends first, and each node's block
  is freed when its owners' share is given back.
- `rust_tree_rc`: each `Rc<Node>` block is 72 bytes (strong 8, weak 8, `Node` 56: checked with a
  compile-time size assertion), so about 72 MB of blocks before the allocator's own headers, plus the
  `Vec<Rc>` children arrays and the 8 MB index: expect clearly more than the model.
- `rust_tree_arena`: run 3's `rust_w2` layout, measured at 52,296 KB (line 21): 32-byte nodes, `Vec<u32>`
  children.

## Workload "w2v": the walk up a tree across a call that may change nodes

### The question

Rules row: "one test of the node's header and one move of the link's weak count (a subtract and an
add), per step | a walk up a tree across a call that may change nodes (R11)". Not measured: run 3's
W2 measured 1.579x of plain C with a header test per step on uncounted links (`model_w2`), safe Rust
1.603x (`rust_w2`), 1.176x with no test (`diag_w2_hop_proved`) (`run3/26-timer.md` lines 20 to 22).
What does the walk cost in each of its forms: the count moves per step, the deferred-drop region, and
the walk whose visit changes no node?

### The program

Run 3's W2 exactly (N = 1,000,000; build; 10 passes of: walk every node up to the root, then move 1%
of the nodes), with one change: every step calls a stored function value, `on_visit(p)`. The visitor
the timed runs store counts the step (`if p.value >= 0: visits.n += 1`), so the walk's own
`depth += 1` moved into it and the checksum is W2's: **647034814 for every program**. The program may
also store `prune` (take the node out of its parent's list, so it and its subtree end), chosen only
when an argument is given, which `runs.txt` never does. Because `prune` can be stored, the call may
end a Node, no view of a node lives across it (R8 (g), `[RC-5]`), and the walk must hold a `weakref`
link (`[WK-18]`), written as E3021's message says:

```ember
for leaf in nodes:
    up = weakref leaf
    while up exists as n:
        if n.parent exists as p:
            up = weakref p
            on_visit(p)
        else:
            break
```

The function value is two words (code, state, R12), read from its slot at every call (a call could
store another function there). The slot is `volatile` in every C program, so neither C compiler
inlines or devirtualises the call; `plain_w2v.c` reads the same slot. The Ember text is the top
comment of `model_w2v.c`.

### The forms, and what each runs per step (from the clang -O2 assembly, `asm/*.s`)

Every form: two loads of the slot, the indirect call, the load of the parent link and its test for
no link. That is the whole step of `plain_w2v` and of `model_w2v_views` (their inner loops are the
same seven instructions, `plain.s` and `views.s`). On top of it:

| binary | when the spec uses it | added per step | added per walk (1,000,000 walks a pass) |
|---|---|---|---|
| `model_w2v_move` | the rule's walk where no region is allowed and the class has no drop: nodes reachable from a `thread_shared` value (`[WK-18]`), counts not atomic since one-owner nodes under the value's lock | header test of `up`; `up = weakref p`: load p's weak count, compare with max, +1, store; -1 on n's weak count and the (never taken) test for 0 | first link: compare, +1; last link: -1 and test |
| `model_w2v_move_drop` | `class Node` has a drop method of its own: no region (`[WK-18]`) and `[WK-17]` condition 1 fails, so `n.parent exists as p` tests p's header too | as `move`, plus a second header test (of p) | as `move` |
| `model_w2v_region` | no drop method, nodes no other thread can end: the deferred-drop region (`[WK-18]`) | header test of `up` only | region counter +1 and -1 (thread-local); first link's compare, +1, -1 |
| `model_w2v_views` | every function the program stores in `on_visit` only reads its node: views (`[WK-18]` last sentence) | nothing | the leaf's open (one header test) |
| `plain_same_w2v` | `model_w2v.c -DPLAIN` | nothing, no checks, model layout | nothing |
| `plain_w2v` | careful C, run 3's plain W2 layout | nothing | nothing |
| `rust_w2v` | safe Rust arena (run 3's `rust_w2` plus the call through a `Box<dyn FnMut(&mut Vec<Node>, u32)>`) | the bounds check of `nodes[a]` | nothing |
| `rust_w2v_rc` | safe Rust with `Rc`/`Weak` (the book's tree), the mechanism `[WK-18]` mirrors | `up.upgrade()` (test, strong +1 with its check, -1 at the end of the step), the parent's `RefCell` borrow and `upgrade` (the same again), `Rc::downgrade` (+1 with check), the old `Weak`'s drop (-1, test) | `leaf.clone()` (+1), the last `Weak`'s drop |

Bridge to run 3 (no call; the walk counts `depth += 1` itself):
- `plain_w2v_novisit`: run 3's plain W2 exactly; it should reproduce run 3's `plain_w2` time.
- `model_w2v_views_novisit`: the proved walk with no call, which is run 3's `diag_w2_hop_proved` walk
  (with this spec's counted parent links in the build and the 1% moves, and `swap_remove` in place of
  run 3's order-keeping `remove`).

### The ratios the lead should read

- The row's cost, as written: `model_w2v_move / plain_w2v` and `model_w2v_move_drop / plain_w2v`;
  their excess over `model_w2v_views / plain_w2v` is the test and count moves alone, since views and
  plain run the same step.
- The region: `model_w2v_region / plain_w2v` (run 3's AN-62 said 0.944 for a region, but measured it
  with no header test per step: `run3/24-faithfulness.md` gap 1; this measures it with the test).
- The free walk: `model_w2v_views / plain_w2v`; `plain_same_w2v / plain_w2v` is the layout's part.
- The call's own weight: `plain_w2v / plain_w2v_novisit`. The call dilutes every per-step cost
  relative to run 3's W2, which had none; the rule exists only where there is a call, so this is the
  honest denominator.
- **As fast as C**: `model_w2v_region` and `model_w2v_views` within a few percent of `plain_same_w2v`,
  and every model form under `rust_w2v_rc`. **Falls short**: `model_w2v_move` or `_move_drop` well
  above `model_w2v_region`; the salvages below then decide what the spec should say.

### Why the comparison is fair

- Same work: the same tree, the same 10 walks of every node to the root, the same 1% moves, the same
  number of calls, the same checksum (647034814 in all thirteen programs).
- Same call: every C program calls through the same `volatile` two-word slot; the Rust programs call
  a `Box<dyn ...>` chosen at run time and passed through `black_box`, so no compiler sees which
  visitor runs.
- Same layout among the model forms and `plain_same_w2v`: the forms differ only in the walk's code
  (the asm confirms it). `plain_w2v` keeps run 3's plain layout so that it stays run 3's baseline.
- The visitor never prunes in the timed runs, so no form ever finds an ended node: what is timed is
  the steady state, the price every step pays for the possibility. `prune` and every region's
  set-aside path are compiled in (and the asm shows them off the hot path), not timed.

### Salvage 1: a deferred-FREE region for a class with a drop method (`salvage_w2v_freeonly.c`)

The rule refuses the deferred-drop region to a class with its own drop method, because deferring the
drop would move a visible action (run 3, AN-62 section 6). The salvage defers less: inside the walk an
object whose last owner ends is ended and dropped at once, exactly as without a region; only the free
of its memory block (when its weak count reaches 0) waits for the region's end. Every link the walk
makes after the first then holds no count. Built with `DROPCLASS`, so compare it with
`model_w2v_move_drop`: same class, same two header tests per step, no count moves.

Safety: a weak count on the walk's link exists only so that the block it names is there for the next
header test. In the region no Node block is freed (the free path tests the per-thread region counter
and sets the block aside), and the link lives only inside the region, so every test reads allocated
memory; if the call ended the object, the test finds the count at 0 and the walk stops, which is the
rule's behaviour. The drop runs when it would have run, so nothing visible moves. The objects are one
thread's (the region's own condition in `[WK-18]`), so no other thread frees a block meanwhile.
What it moves elsewhere: one test of the region counter on the free path of every block of a class
some walk keeps uncounted links to, and the memory of the blocks freed during one walk, held until it
ends.

### Salvage 2: version the walk on the function actually stored (`salvage_w2v_dispatch.c`)

The compiler knows every function the program may store in `on_visit` (R12, whole program) and what
each may change (R5). At each walk's start the stored code word is compared with the ones that change
no node (`count_visit` here); if it is one of them, the views walk runs (nothing per step); otherwise
the rule's walk (`model_w2v_move`'s). One load and one compare per walk, and a second copy of the
walk's code.

Safety: the views walk runs only while the stored function is one whose summary changes no node, the
case the spec already allows when a program never stores a pruner; no call in it can end a node, so
the views stay valid. The test holds for the whole walk because no storable function writes
`on_visit` (its summary says so); where one could, the test moves to every step, still touching no
node. Its gain is for programs that can store a pruner but usually store a reader: when the pruner is
stored, it pays the rule's walk in full.

### Salvage 3: one region per pass, and an uncounted first link (`salvage_w2v_hoist.c`)

Compare with `model_w2v_region`. Two changes: the region covers the whole pass of walks (entered once
per pass, not per walk), and the walk opens its leaf first, `if leaf exists as n: up = weakref n`, so
even its first link is given a live node inside the region and holds no count. Per walk: the leaf's
open (one header test, which the region form's first `while` test also does); per step: the header
test.

Safety: R11's own rule applied twice. A link that lives only inside the region and is given only an
object that lives at that moment holds no weak count; `n` is opened that instant, so `up = weakref n`
qualifies as `up = weakref p` does, and opening the leaf first runs the same test the first loop test
would, so the walk visits the same nodes. The region around the pass keeps every object ended during
the pass set aside (ended, its block kept) until the pass ends, so every uncounted link of every walk
names a block still there. What it costs: the memory of nodes ended during a pass is held until the
pass ends rather than the walk (none in the timed runs).

### Salvage 4 (measured by an existing binary): the region under a held lock

`model_w2v_move` is the form for one-owner nodes reachable from a `thread_shared` value, where
`[WK-18]` refuses the region because "another thread may end" them. If the walk runs inside the
`with x.lock:` that guards them, no other thread can end one during it (a `thread_shared` value is
changed only through its lock, an atomic or a channel: E7014), so the region's condition holds and
the walk can be `model_w2v_region`'s. Its cost is that binary's; it needs only a wider condition in
`[WK-18]`: "not reachable from a `thread_shared` value, or reached only inside the lock that guards
it, held for the whole walk".

### Memory (the expected peaks, and why)

- `plain_w2v`, `plain_w2v_novisit`: run 3's `plain_w2`, 54,940 KB (`run3/26-timer.md` line 20); the
  call adds nothing.
- Every model form, `plain_same_w2v` and every salvage: run 3's `model_w2` layout, 84,368 KB (line
  22), the 48-byte objects and the index. The weak counts live in the header that was already 12
  bytes. The regions hold nothing in the timed runs (no node ends during a walk); with `prune` stored,
  a region per walk holds at most what one walk's calls end, a region per pass (salvage 3) what one
  pass's calls end, and the deferred-free region only the bare blocks (the drops ran).
- `rust_w2v`: run 3's `rust_w2`, 52,296 KB (line 21).
- `rust_w2v_rc`: 72-byte `Rc<Node>` blocks plus the `Vec<Rc>` children and the 8 MB index of `Weak`s:
  expect clearly more than the model.

## Open doubts

1. **The tree checksum is not known.** M2 may not run programs, so `runs.txt` says every tree program
   must print what `plain_tree.exe` prints. The w2v checksum is known (647034814) because the visitor
   counts exactly what run 3's walk counted.
2. **The cost table names the wrong Rust program.** Rules section 2 calls `rust_w2` "safe Rust's walk,
   which upgrades a `Weak` on every step (a count pair)"; `target/redesign2/bench/rust_w2.rs` is an
   index arena with no `Rc` or `Weak` at all, and its 1.603x is bounds checks and layout.
   `rust_w2v_rc` is the walk that really upgrades a `Weak` per step.
3. **The row's "one test and one move per step" applies to one case only.** With a drop method,
   `[WK-17]` condition 1 fails and the parent read tests too: two tests and one move per step
   (`model_w2v_move_drop`). The single-test form arises for one-owner nodes reachable from a
   `thread_shared` value (`model_w2v_move`); for nodes that are themselves `thread_shared` the counts
   are atomic and each open is a compare-exchange loop (`[WK-12]`), which neither binary models.
4. **Region per walk or per pass.** `[WK-18]` says the walk is placed in a region whose memory is freed
   "when the walk ends"; I read that as one region per walk (`model_w2v_region`) and measured the per-pass
   reading as a salvage (`salvage_w2v_hoist`).
5. **The weak -1 on the old target of `up = weakref p`** keeps Rust's test for zero, though the
   target was tested alive just before and nothing between could end it. No rule lets the compiler
   drop that test, so the model keeps it; it is a branch never taken.
6. **A C programmer's protection.** `plain_w2v` is the unprotected walk (reading `a->parent` after the
   call), safe only because the timed visitor never frees. A C program with a pruning callback would
   need its own protection; that is the point of the rule, and why the baseline is unprotected.
