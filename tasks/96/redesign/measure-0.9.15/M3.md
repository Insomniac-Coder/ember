# M3: the cost of `using A` and of the instance word (spec 0.9.15_Hardened_1, R3, verdict 47)

Measurement agent M3. Brief: `measure-0.9.15/inputs/brief.md`. Nothing here was run: every program was
compiled once (clang 22.1.8 `-O2`, rustc 1.98.1 `-C opt-level=2 --edition 2021`) to check that it
builds, and every number below is layout arithmetic, marked so, never a timing. The lead runs the
timings (`M3/runs.txt`).

## The rows

From section 2 of `run4/v5/rules.md`:

| row | rule | what this job measures |
|---|---|---|
| "the memory manager's own work, each allocation and free of a value with `using A` ... (an arena: a pointer bump, nothing freed one by one); not measured" | R3, [ALC-1], [ALC-2], [ARN-2] | W1 and W2: Ember's arena against malloc/free and against the C programmer's own arena; Rust's hand-written arena |
| "one word in the value: its instance's address ... Rust's `Box<T, &A>` and `Vec<T, &A>` keep the same word; not measured" | R3, [ALC-1], verdict 47 | W1 (many small values), W2 (growing lists), W3 (a manager that frees single values): speed and memory, with and without the word |
| verdict 47's two ways to drop the word: (a) a kind that never frees single values, (b) memory laid out so a pointer finds its arena | verdict 47 | a salvage program for each, in every workload where it applies |

What the spec says, in the words the programs follow:
- [ALC-1] / R3: "A value whose manager may have several instances keeps its instance's address, one
  word, so that its growth and its end go back to the instance it came from." `Arena` has several
  instances, so every `owns T using Arena` place and every `Array[T] using Arena` keeps the word.
- [ARN-2]: a value made in an arena with `using` has an end that "runs its `drop` and gives its block
  back to the arena, which frees nothing one by one".
- [ALC-2]: `allocate` returns null on failure; [ALC-4]: a failed allocation panics; [HEAP-8]: a
  capacity whose byte size overflows panics before allocating; [HEAP-2]: lists grow by doubling from 4.
- [ALC-5] and E3063: a value made in an instance lives no longer than it, and `reset()` is refused
  while one lives. Both are checked when compiling, from the making line (`using current`), not from
  the stored word. That is why every salvage below keeps the same safety: they only change how the
  instance is found at run time, never what the compiler proves.

## Files

All sources are in `tasks/96/redesign/measure-0.9.15/M3/`, binaries in `target/measure-0.9.15/M3/bin/`.

| file | what it is |
|---|---|
| `harness.h`, `rharness.rs` | copied unchanged from `artifacts/bench/harness.h` and `artifacts/redesign2/bench/rharness.rs` (run 3's Rust twin: same LCG, same output line) |
| `m3_rt.h`, `m3_rt.c` | the memory managers every C program shares, one copy each (below) |
| `m3_bump.rs` | the hand-written arena every Rust program shares: `Bump`, `ABox<'a, T>` (= `Box<T, &'a Bump>`), `AVec<'a, T>` (= `Vec<T, &'a Bump>`) |
| `build.txt`, `runs.txt` | every build line (the file runs as a bash script); every run line |

The memory managers in `m3_rt.h` / `m3_rt.c`:
- **`RtArena`** is a port of today's runtime arena (`runtime/ember_rt/src/ember_rt.c`, "arenas":
  1 MB chunks from the global allocator, a chunk list, `reset` rewinds every chunk and keeps it). Its
  entry points (`rt_arena_alloc_uninit` = `ember_arena_alloc_uninit`, `rt_arena_reallocate`,
  `rt_arena_deallocate`, `rt_arena_reset`) live in `m3_rt.c`, compiled as its own translation unit
  and never `#include`d, so no call into it can be inlined, exactly as a call into `ember_rt` is
  today. `rt_arena_bump` / `rt_arena_grow_inl` are the same arena's fast path written inline.
- **`HArena`** is way (b): chunks on 64 KB boundaries (VirtualAlloc's granularity), each starting
  with a 64-byte header that holds the arena's address, so
  `h_arena_of(p) = ((HChunk *)(p & ~0xFFFF))->arena`. A block bigger than a chunk gets a region of
  its own that starts 64 bytes after its header, so the mask still finds it; a reset keeps those
  regions for the next big block, as the runtime keeps its chunks.
- **`Pool`**: one block size, a free list through the free blocks, 64 KB slabs from VirtualAlloc,
  each slab starting with a 64-byte header `{pool, next slab}` (the slab list every pool keeps to
  free itself; only way (b) reads the pool from it).

Every C struct whose size this report states has a compile-time size check
(`typedef char size_check_X[sizeof(X) == N ? 1 : -1]`), and every Rust one a `const` assert, so the
layout numbers below are checked by the compilers, not assumed.

## W1 "trees": many small values made in an arena

**The question.** For values made `owns T using Arena`, what does Ember's arena cost per allocation
and per end, against malloc/free and against the C programmer's arena; and what do the instance
word and the end of each value cost, in time and in memory?

**The work** (every program): 16 batches; each batch builds random expression trees until it holds
at least 2^20 nodes, all alive at once (a leaf holds a number, an inner node an operator and two
children: the nodes of a parse, the arena's classic use); evaluates every tree; ends them all. The
tree shape comes from `h_rand()` (seed 42): a node at depth 0, or when `r & 3 == 0`, is a leaf with
`(r >> 2) % 100`; else an operator `1 + (r >> 2) % 3` (add, multiply, subtract, u32 wrapping) whose
children are built first, then the node is allocated (so every program allocates in the same order).
Checksum: per tree `cs = cs * 1000003 + value`, per batch `cs += nodes`.

The Ember program (the full text is in `model_trees.c`'s header):

```ember
enum Expr:
    Leaf(val: int32)
    Bin(op: int32, left: owns Expr using Arena, right: owns Expr using Arena)

    ...
    return owns Expr.Bin(op=1 + (r >> 2) % 3, left=left, right=right) using arena
```

**The programs.**

| program | node | link | allocation | a tree's end |
|---|---|---|---|---|
| `plain_trees_malloc` | 24 B | 8 B pointer | `malloc` | a post-order walk of `free` |
| `plain_trees_arena` (the C to match) | 24 B | 8 B | `RtArena`, inline bump | nothing; one `reset` per batch |
| `model_trees` (the rule as written, today's runtime) | 40 B | 16 B `{block, instance}` (R3) | `ember_arena_alloc_uninit`, a call into the runtime ([ALC-1]), then the null test ([ALC-4]) | a walk; each node's `deallocate(word, p, Layout(40, 8))`, a call of an empty runtime function ([ARN-2]) |
| `model_trees_inl` (`-DM3_INLINE`) | 40 B | 16 B | the same arena's bump compiled into the program, null test | a walk; the empty `deallocate` inlined, so the walk alone |
| `model_trees_inl_nowalk` (`-DM3_INLINE -DM3_NOWALK`) | 40 B | 16 B | inline, null test | nothing (see below) |
| `salvage_trees_chunkhdr` (way (b)) | 24 B | 8 B | `HArena`, inline, null test | a walk; each node's instance found from its address, `deallocate` empty |
| `salvage_trees_nofree` (way (a)) | 24 B | 8 B | `RtArena`, inline, null test | nothing |
| `rust_trees box` | 24 B | `Box<Expr>` | global allocator | drop walk + free |
| `rust_trees abox` | 40 B | `ABox<'a, Expr>` = `Box<Expr, &'a Bump>`, 16 B | `Bump`, inline | drop walk, `dealloc` a no-op through the kept `&Bump` |
| `rust_trees bref` | 24 B | `&'a Expr` (bumpalo's `alloc` idiom) | `Bump`, inline | nothing; `reset(&mut self)` |
| `rust_trees index` | 16 B | `u32` index into one `Vec<ExprI>` per batch, bounds-checked | `Vec::push` | `clear()` |

Two forms of the model, because the spec does not fix them:
- **Runtime call or inline.** `std/src/arena.em` says "The arena operations themselves are the
  compiler's", and today they are runtime calls (`ember_arena_alloc_uninit`). Nothing in the spec
  stops the compiler inlining the bump. `model_trees` is today's emission, `model_trees_inl` the
  best the rule's emission can do; their difference is the price of the runtime call, not of the
  rule.
- **The walk.** Ending a tree means ending each node, and each node's end calls `deallocate` through
  its word. `Arena` is compiler-known and [ARN-2] says its `deallocate` frees nothing; `Expr` has no
  drop of its own. So a compiler may prove that ending a tree runs nothing and skip the walk. The spec
  does not say it must, so both forms are written: `model_trees_inl` (walk) and
  `model_trees_inl_nowalk` (word kept, walk proved away). I checked in the assembly that clang keeps
  the walk when it is written (`drop_expr` is still called recursively in `model_trees_inl` and
  `salvage_trees_chunkhdr`): clang cannot prove a recursive function returns, so it cannot delete it.

**Why the comparison is fair.** One random sequence, one allocation order (children before parent),
one evaluation, the same 1 MB chunk arena (`RtArena`) in `plain_trees_arena`, all `model_trees*` and
`salvage_trees_nofree`; the roots list is a malloc'd array grown by doubling and freed every batch in
every C program (Ember must end it before `reset`, [ALC-5]; C does the same so the work matches).
Layouts differ only where the rule makes them differ (the 16-byte links), except `rust_trees index`
(16-byte nodes, u32 links: safe Rust's other arena, a different layout, shown for reference) and
`salvage_trees_chunkhdr` (64 KB chunks instead of 1 MB: one slow-path call per ~2,700 nodes instead of
per ~43,000; both rare).

**Reading the results.** Each pair isolates one thing:

| pair | what the difference is |
|---|---|
| `model_trees` vs `model_trees_inl` | the runtime call per allocation and per end (implementation, not the rule) |
| `model_trees_inl` vs `model_trees_inl_nowalk` | the walk at the end, with the word |
| `salvage_trees_chunkhdr` vs `salvage_trees_nofree` | the walk at the end, without the word |
| `model_trees_inl_nowalk` vs `salvage_trees_nofree` | **the word alone**: 16 more bytes per node, so more cache lines to build and evaluate |
| `salvage_trees_nofree` vs `plain_trees_arena` | the null test after each allocation (expected nothing) |
| `plain_trees_malloc` vs `plain_trees_arena` | what an arena saves C: the allocator's own work per value |
| `rust_trees abox` vs `model_trees_inl` | Rust's `Box<T, &A>` doing the same thing |
| `rust_trees bref` vs `salvage_trees_nofree` | Rust's arena idiom vs way (a) |

"As fast as C" for the row as written: `model_trees_inl` within the run-to-run spread of
`plain_trees_arena`. "Falls short": outside it; the pairs above then say whether the word, the walk
or the call is the cause. The memory side is certain before running (below): the rule as written
costs 67% more node memory in this workload.

**Memory: expected peaks (layout arithmetic, not measured).** A batch holds 2^20 nodes plus at most
one tree's overshoot (a tree averages about 390 nodes: E(d) = 1 + 1.5 E(d-1), E(0) = 1, so
E(12) = (1.5^13 - 1) / 0.5 ≈ 387):

| program | node data at the peak | why |
|---|---|---|
| `plain_trees_arena`, `salvage_trees_nofree`, `salvage_trees_chunkhdr`, `rust_trees bref` | 2^20 × 24 B = 24 MiB, in 1 MiB chunks (64 KiB for chunkhdr) | 24-byte nodes, nothing per value |
| `model_trees*`, `rust_trees abox` | 2^20 × 40 B = 40 MiB | two 16-byte links per node: **+16 MiB, the word** |
| `plain_trees_malloc`, `rust_trees box` | about 32 MiB (estimate) | 24-byte blocks plus the Windows heap's per-block header and 16-byte rounding |
| `rust_trees index` | 16 MiB live, but about 32 MiB at the moment the `Vec` doubles from 2^20 to 2^21 entries (the old and new buffers both touched during the copy) | 16-byte nodes, `Vec` growth |

Plus a few MiB of process baseline in every program. The roots lists are about 2,700 entries: 22 KB
at 8 B, 43 KB at 16 B.

## W2 "lists": growing lists made in an arena

**The question.** For `Array[T] using Arena` (verdict 47: "a list is made in an arena the same way,
`[String("a")] using current`"), what do the word and the arena's growth cost, in time and memory,
on many small lists that grow?

**The work**: 24 frames of a spatial grid, the classic per-frame list: each frame makes 2^18 empty
cell lists, puts 2^20 entity ids into random cells (`cells[h_rand() % 2^18].push(...)`, each list
growing from 4 by doubling), reads every cell, then ends every list and resets the frame arena.
Checksum: per cell `s = Σ v[k] · (k + 1)`, `cs = cs · 1000003 + s + len`.

**The programs.**

| program | list header | growth | the frame's end |
|---|---|---|---|
| `plain_lists_malloc` | 24 B `{data, len, cap}`; the cell array malloc'd once and kept | `realloc` | `free` per list |
| `plain_lists_arena` (the C to match) | 24 B; the arena passed where a list grows; the cell array in the arena | `RtArena`, inline: in place when the buffer is the arena's last block, else a new block and a copy | one `reset` |
| `model_lists` (as written, today's runtime) | 32 B `{data, len, cap, instance}` (R3); the cell array in the arena (`Array.new_in(frame)` + `reserve(G)`) | through the word: `allocate` the first time, `reallocate` after, runtime calls; [HEAP-8] check, [ALC-4] null test | each list's `deallocate` through its word (an empty runtime call), then `reset` |
| `model_lists_inl` (`-DM3_INLINE`) | 32 B | the same, inline | `deallocate` inlined to nothing |
| `salvage_lists_known` (way (a+)) | 24 B | the instance passed where the list grows, as C does; the same checks | `reset` |
| `salvage_lists_chunkhdr` (way (b)) | 24 B | the instance from `data & ~0xFFFF`; the same checks | `reset` |
| `rust_lists vec` | `Vec<u32>`, 24 B; the outer `Vec` kept | global allocator (`RawVec`'s first capacity for 4-byte elements is 4, then doubling: the same sizes) | drop + free |
| `rust_lists avec` | `AVec<'a, u32>` = `Vec<u32, &'a Bump>`, 32 B; the outer list an `AVec` in the frame arena | through the kept `&Bump` | `reset(&mut self)` |

The model makes the cell array in the frame arena because it must: a list holding values made in
`frame` may not live across `frame.reset()` ([ALC-5], E3021), so it is made and ended every frame,
and in the arena that costs no page faults per frame (the arena keeps its chunks). Safe Rust is
forced the same way by `reset(&mut self)`. `plain_lists_arena` does the same, so the C to match does
the same work.

**Checks that are not this row's.** Ember bounds-checks `cells[i]` (today's check, "not this
rework's" in the cost table), and the growth path has [HEAP-8]'s capacity check and [ALC-4]'s null
test. They are kept in the model and in both salvages, so `model_lists_inl` vs the salvages measures
the word only; `plain_lists_arena` has none of them, so `salvage_lists_known` vs `plain_lists_arena`
measures those checks (expected small: one compare per push, never taken).

**Reading the results.**

| pair | what the difference is |
|---|---|
| `model_lists` vs `model_lists_inl` | runtime calls on growth and end (implementation) |
| `model_lists_inl` vs `salvage_lists_known` | **the word**: 8 more bytes per header (2 MiB more over 2^18 lists, so more cache misses on the random pushes), and the instance loaded from the list at each growth |
| `salvage_lists_chunkhdr` vs `salvage_lists_known` | finding the instance from the buffer's address (an AND and a load) at each growth, about 1.37 growths per list per frame |
| `salvage_lists_known` vs `plain_lists_arena` | the bounds, capacity and null checks |
| `plain_lists_malloc` vs `plain_lists_arena` | what the arena saves C |
| `rust_lists avec` vs `model_lists_inl` | Rust's `Vec<T, &A>` doing the same thing |

"As fast as C": `model_lists_inl` within the run-to-run spread of `plain_lists_arena` plus the checks'
cost (`salvage_lists_known`). "Falls short": outside it.

**Memory: expected peaks (arithmetic, not measured).** With 2^20 ids in 2^18 cells, a cell's length is
close to Poisson(4): 1.8% empty, 61.1% of length 1-4 (capacity 4, 16 B), 35.0% of length 5-8
(capacity 8), 2.1% longer (capacity 16; capacity 32 has probability about 10^-6). In an arena a list
that grew keeps its old buffers until the reset (random pushes almost never hit the arena's last
block), so the buffers take 16·0.611 + 48·0.350 + 112·0.021 ≈ 29 B per cell, 7.2 MiB per frame;
with realloc only the final buffer stays: 16·0.611 + 32·0.350 + 64·0.021 ≈ 22 B, 5.6 MiB, plus the
heap's per-block header and rounding.

| program | headers | buffers | why |
|---|---|---|---|
| `plain_lists_arena`, `salvage_lists_known`, `salvage_lists_chunkhdr` | 2^18 × 24 B = 6 MiB | 7.2 MiB | |
| `model_lists*`, `rust_lists avec` | 2^18 × 32 B = 8 MiB | 7.2 MiB | **+2 MiB, the word** (+15% of the frame's memory) |
| `plain_lists_malloc`, `rust_lists vec` | 6 MiB | about 5.6 MiB of data plus heap overhead (estimate) | |

The runtime arena also never returns to its first 1 MiB chunk once a bigger block moved it on
(`arena_alloc_raw` walks forward from the current chunk), so `RtArena` programs carry about 1 MiB
unused; the same in the plain arena and in the model.

## W3 "churn": a memory manager that frees single values

**Why this workload.** An arena frees nothing one by one, so for W1's values the word is only ever
used for growth that never comes. The word exists for managers that do give single blocks back
("so that its growth and its end go back to the instance it came from"). W3 measures that case, and
way (b) for it (way (a) cannot apply: this kind frees).

**The question.** For `owns T using Pool` where `Pool` has several instances and frees each value at
its end, what does the word cost against C, and does way (b) remove it at no cost?

**The work**: run 3's W3 pool (blocks on a free list, `artifacts/bench/plain/w3.c`) with two
instances. 2^18 slots each own one 32-byte object made in its team's pool; 2^25 steps each pick a
random slot (`(r >> 3) % 2^18`), update its object, and when the object's hp runs out end it (its
block back to its own pool) and make a new one in a random team's pool, the new one made before the
old one ends (Ember's and Rust's `=`; the C programs do the same so the free lists are reused in the
same order). Roughly a third of the steps end an object and make another. Checksum: per step
`cs += score ^ id`, per ended object `cs += score`, at the end `cs += objects made`.

**The programs.**

| program | slot | where an end goes |
|---|---|---|
| `plain_churn_malloc` | 8 B | `free` |
| `plain_churn_pool` (the C to match) | 8 B | `pools[o->team]`: the C programmer knows the object's own `team` field names its pool; a compiler cannot know that |
| `model_churn` (as written) | 16 B `{block, pool}` (R3) | `deallocate` through the word; the pool is the program's own `Allocator`, compiled into the program, so inline; `slots[i]` and `pools[team]` bounds-checked, [ALC-4] null test |
| `salvage_churn_chunkhdr` (way (b)) | 8 B | the pool from the slab header: `pool_of(p)`; the same checks |
| `rust_churn box` | `Box<Obj>`, 8 B | global allocator |
| `rust_churn pbox` | `PBox<'a, Obj>` = `Box<Obj, &'a Pool>`, 16 B | through the kept `&Pool` (the same pool algorithm, hand-written) |
| `rust_churn slab` | u32 (top bit: the team) into two `Vec<Entry>` with a free list, bounds-checked and matched | the slab's free list; a 40-byte entry (a different layout, for reference) |

**Reading the results.** `model_churn` vs `salvage_churn_chunkhdr` is the word alone (8 more bytes per
slot: 4 MiB instead of 2 MiB of slots, randomly accessed, against one AND and one load of a slab
header at each end; there are about 130 slabs, so their headers stay in cache). `salvage_churn_chunkhdr`
vs `plain_churn_pool` is the two bounds checks and the null test. `rust_churn pbox` vs `model_churn`
is Rust's `Box<T, &A>` doing the same. "As fast as C": `model_churn` within the spread of
`plain_churn_pool` plus the checks; "falls short": outside it.

**Memory (arithmetic, not measured).** Objects: 2^18 × 32 B = 8 MiB, in slabs of 2,046 blocks
(64 KiB minus the 64-byte header, over 32 B), about 130 slabs. Each pool's live count stays near
2^17: the team of each new object is random and the team of each ending object follows the live
counts, so the difference between the pools reverts to zero (its spread is about √(2^18) / 2 = 256
objects, 8 KiB). Slots: 2 MiB at 8 B (`plain_*`, `salvage_churn_chunkhdr`, `rust_churn box`), 4 MiB at
16 B (`model_churn`, `rust_churn pbox`): **+2 MiB, the word**. malloc'd objects: 32-byte blocks plus
the heap's header and rounding, about 12 MiB (estimate). `rust_churn slab`: 40-byte entries in two
`Vec`s of about 2^17 entries each, about 10 MiB, more while a `Vec` doubles.

## Verdict 47's two ways, side by side

| | (a) a kind that never frees single values | (b) memory laid out so a block finds its instance |
|---|---|---|
| removes the word for | fixed-size values (`owns T using A`, class objects `using a`): they never grow, and their end gives nothing back | every value of a kind that makes the promise, growing lists and freeing kinds included |
| does not cover | growing lists (growth needs the instance); kinds that free (W3) | kinds that cannot lay their memory out so (an allocator over a foreign heap, `Global`) |
| also removes | the walk at a tree's end, when T has no drop of its own (W1: `salvage_trees_nofree`) | nothing else: each end still runs and finds its instance (W1: `salvage_trees_chunkhdr` keeps the walk) |
| run-time cost | none | one AND and one load per growth or free (the chunk's header); none where `deallocate` is empty, since the load is then dead |
| memory cost | none | a 64-byte header per 64 KiB chunk (0.1%); chunks aligned to their size; a block bigger than a chunk needs a region of its own whose header precedes it |
| needs from the language | the `Allocator` kind declares it, checked when compiling: e.g. `unsafe extend Arena implements Allocator(frees_nothing):`, whose `deallocate` must then be empty; the compiler's "needs drop" test counts `owns T using A` of such a kind as needing drop only when T does | one more unsafe promise an `Allocator` kind may make, e.g. `fn instance_of(p: *mut u8) -> sharedref mut Self`; a kind that makes it gets no word in its values; nothing in the program's text changes |
| what stays checked | E3063 (no value outlives its instance) and [ALC-5] (no reset under a live value): both read the making line, not the word | the same, unchanged; the instance found is the one the block came from by the kind's promise, the same kind of promise [ALC-2] already asks of an implementer ("valid, aligned, unaliased memory") |
| precedent | bumpalo's `Box<'a, T>` and `alloc` (`&'a mut T`, no arena word); `rust_trees bref` | jemalloc/mimalloc find a block's metadata from its address the same way (segment alignment); `HArena` and `Pool` here |

**(a+) the instance known where a list grows** (`salvage_lists_known`). (a) alone keeps the word for
lists. The C programmer passes the arena where a list grows; Ember can do the same when every growth
site knows the instance when compiling, which holds when the place's type names the instance, not
only the kind (`cells: Array[Array[u32] using frame] using frame`, `frame` a name in scope, as a Rust
lifetime brand). The cost is in the language, not at run time: a list given to a function needs the
instance given too (`fn add(ref mut l: Array[u32] using a, ref mut a: Arena)`), more to write and to
read than verdict 47's form; a list whose instance is not known where it grows keeps the word. Safety
is kept because the instance passed is the one the type names, checked when compiling.

**The two together.** (a) for fixed-size values in no-free arenas (no word, no walk) and (b) for growing
lists and freeing kinds would remove the word everywhere a kind can align its memory, with no
change to any program's text; only kinds that cannot (foreign heaps) would keep it, and `Global`
and `System` never had it.

## Ideas seen but not modelled

- **One word per list, not per element.** `roots: Array[owns Expr using Arena]` stores the same
  instance in every element. A rule that every element of one list comes from one instance (checked
  when compiling, as E2020 checks the kind) would keep one word in the list's header. W3's slots come
  from two pools, so that program would need two lists. Not modelled: (b) already removes the word.
- **The instance's index in the pointer's spare bits.** A 32-byte-aligned block has 5 free low bits:
  an index into a per-kind table of instances, for kinds that cannot align their chunks. It costs a
  mask on every use of the pointer, and a table whose entries must not be reused while values live.
  Weaker than (b) where (b) applies.
- **One instance per thread.** R3 already says a manager with one instance costs no word; an arena
  kind with one instance per thread (today's `jobs.local_arena()`) is that case and needs nothing new.

## Open doubts

1. No checksum value is known: nothing was run. `runs.txt` marks which programs must agree.
2. The malloc peaks are estimates of the Windows heap's per-block overhead (header and 16-byte
   rounding), not documented figures; the lead's `peak_kb` will show the real ones.
3. The MSVC build was not tried (no `cl` on this PATH). The C is plain C11 (checked with clang
   `-std=c11 -pedantic`, no warnings); `M3_NOINLINE` / `M3_LIKELY` hide the compiler-specific parts.
   Building with `/GL` would let MSVC inline `m3_rt.c` and erase the runtime-call form's meaning.
4. Whether Ember's compiler will prove the walk away (`model_trees_inl_nowalk`) is not settled by the
   spec; both forms are there.
5. `Arena`'s `reallocate` does not exist in today's runtime (0.9.15 makes `Arena` implement
   `Allocator`); `rt_arena_reallocate` is the natural bump growth (in place when last, else copy), the
   same as the C programmer's and bumpalo's.
