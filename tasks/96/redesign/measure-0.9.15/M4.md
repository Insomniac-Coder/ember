## 1. `this` without noalias (verdict 18; R4 last point, R5; [BRW-22], [EXC-15], [SIMD-3])

### The question

A method that changes its object is compiled with `Game *` and no `restrict`. A link may lead back to
the object (the turret aimed at itself), so `this` is never its object's only name. Rust's
`&mut self` is noalias. How much speed does Ember lose in loops where that could matter?

The loops tested are a loop over a list the object owns that reads and writes the object's own
fields. That is the shape area-B named (AN-17's `tick`), plus two harsher ones where element stores
have the same C type as the fields. With the same type, clang's type-based alias analysis cannot
keep the two apart.

### The programs

The three workloads use the same set of programs.

| program | what it models |
|---|---|
| `plain_this_<wl>` | Careful C: `void f(T *o)`, with fields used where the method uses them and the walked list's words read once. No checks. |
| `plain_this_<wl>_noalias` | The same C with `restrict` on the object pointer (`-DNOALIAS_THIS`). This is what Rust's `&mut self` gives LLVM. |
| `model_this_<wl>` | The rule as written. `this` has no `restrict`. It has the 8-byte class header ([OBJ-1]), every `+=`/`-=` checked ([TYP-8]), and the bounds test of `hist[x & 255]` ([TYP-31]: the index is proved in 0..255, but `hist.len` is not known when compiling). `this_mix` has the [OPT-2] entry test plus checked body. The walk reads the list's words once (R8 (c)). |
| `salvage_this_<wl>_typeproof` | The model with `restrict` on `this` (salvage A). |
| `salvage_this_<wl>_hoist` | The model with the fields the loop uses held in locals (salvage B). |
| `rust_this_<wl>` | `fn f(&mut self)`, `#[inline(never)]`. `this_tick` uses `Vec<Box<Player>>`; `this_mix` uses `zip`. |

Every method is `NOINLINE`. The object passes through `launder()` (a volatile store and load). Without
that, clang inlines the method into `main`, sees that the object came fresh from `calloc` (so nothing
else can point at it), and keeps every field in a register in every variant. A first build did
exactly that, and all five C variants compiled to the same loop. No caller of a real method can
assume that, so the laundered build is the fair one.

### Why the comparison is fair

- **Same layout.** The players are carved in order from one block in every C program, as a slab
  carves class objects. The model adds the 8-byte header to each object. Rust's `Box`es come from the
  system heap, with no header.
- **Same work and checksum.** `this_tick` keeps AN-17's death path: count the death, respawn the
  player, call `note`, which pushes onto `log`. About 33 deaths per frame.
- **The model-versus-plain ratio mixes two things:** the checks, and the missing noalias. The
  **noalias cost on its own is `model / salvage_typeproof`** (same code and checks, `restrict` added),
  and for plain C it is `plain / plain_noalias`.

### What the assembly already shows (clang -O2; facts to check against the timings)

| wl | without `restrict` (plain and model) | what `restrict` changes | what hoisting changes | Rust `&mut self` |
|---|---|---|---|---|
| tick | `damage` reloaded every iteration; `total_hp` stored every iteration | nothing in the hot path: `push`'s out-of-line `arr_grow(&this->log...)` receives a pointer into the object, so the compiler still assumes it may write any field | `damage` in a register; `total_hp` stays in a register until after the loop | same as the C model without `restrict`: `damage` reloaded, `total_hp` added in memory (the `grow_one(&mut self.log)` call defeats it too) |
| tally | plain: `hist.ptr` reloaded, `total` added in memory, `max` loaded each time. Model: `hist.ptr` and `hist.len` reloaded (the bounds test), `total` loaded and stored | model: only `hist.len` moves into a register; `total` is still loaded and stored (the checks' panic exits keep the store in the loop) | all of `hist.ptr`, `hist.len`, `total` and `max` in registers | `total` in a register but stored each iteration |
| mix | `gain` reloaded and `peak` compared in memory every iteration | `gain` in a register; `peak` stored only when it grows | `gain` and `peak` in registers (`maxsd`) | as C with `restrict` |

So the prediction is:
- `restrict` on `this` buys little where the loop's cold path calls out of line (tick) or has panic
  exits (tally);
- the front end's hoist buys what `restrict` was supposed to buy;
- Rust's `&mut self` does not beat the C model on tick.

### What would count as "as fast as C" and as "falls short"

- **As fast as C:** `model` within 5% of `salvage_typeproof`. Then the missing noalias costs nothing
  measurable, and the model's distance from `plain` is the checks' cost, which belongs to other rows.
- **Falls short:** `model` slower than `salvage_typeproof` by more than the noise, or slower than
  `rust_*` by more than the checks explain.
- If `salvage_hoist` is clearly faster than `model`, then **the hoist recovers the loss, with nothing
  checked at run time**, whatever the noalias verdict.

### Salvage

- **A, `typeproof`:** give `this` noalias for one method when the compiler proves no pointer the
  method, or anything it calls, dereferences can lead to an object of `this`'s class (or of a base
  class or interface of it).
  - Safety: [SIMD-3] already lets `this` take an alias fact "when the compiler proves that no other
    path the loop uses reaches the same object (the two have different types ...)". Salvage A widens
    that from one loop to the whole method.
  - The proof is the compiler's own place analysis: R5 works out every place a function reaches.
  - The turret dereferences a link of its own class, so the proof fails for it, and it keeps today's
    emission.
  - Nothing runs while the program runs.
- **B, `hoist`:** the front end reads into a local each field the loop only reads, keeps each field
  only the loop changes in a local, and writes it back after the loop. It also writes back before any
  call in the loop that reads that field; `note` reads only `log`, so none is needed here.
  - Safety: the facts are the ones R5/R8 already compute. Every write in the loop goes to:
    - another class's object (`p.hp`);
    - a buffer the object owns, which is never the object's own block;
    - a field the loop itself owns.
  - A panic aborts with no unwinding ([PAN-1]), so a field that has not been written back is never
    seen.
  - Where the proof fails (a write through a link of the method's own class, or a call that reads a
    cached field), the field is used in place, as in the model.
  - This is [SIMD-3]'s per-loop alias fact, made by Ember itself instead of asked of the C compiler.
    It also works under MSVC, which ignores most of what `restrict` could buy.

### Memory (the expected peak, and why)

Every program has a process floor of about 4 MB. Run 3's W4 measured 4,072 KB for plain C and
4,476 KB for Rust with almost no data. Each workload adds this data on top:

- **tick:**
  - plain C: 655,360 B of players (40 B each) + 131,072 B of pointers;
  - model: + 131,072 B more (the 8-byte header on each of the 16,384 players);
  - Rust: every `Box` from the heap (40 B + heap overhead) + 131,072 B for the `Vec`;
  - `log` stays under 1 KB in all of them.
- **tally:** 524,288 B of samples + 2 KB of buckets, the same in every program.
- **mix:** 2 x 524,288 B, the same in every program.

The salvages allocate exactly what their model does.

## 2. One whole variable under two names (verdict 88; R4 exception 1; [BRW-11] exception 1, [BRW-22], [SIMD-3] (e))

### The question

`add_both(ref mut x, ref mut x)` is allowed: the call is compiled against a copy of the function in
which the two names are one. Two things to find out:
1. How fast is that copy?
2. How much code can the copies cost?

### Speed: `samevar`

The workload is the function from run 2's `span_add.c`, the shape behind AN-14's 1.53x:

```
blend(ref mut dst: MutSpan[f32], ref mut src: MutSpan[f32]):
    dst[k] = dst[k]*0.5 + src[k]*0.25
    src[k] = src[k]*0.75 + 0.125
```

- 50,000,128 calls, out of line, on 16-float spans.
- The span length is read from a volatile, so it is not known when compiling: a function compiled
  once for every caller.
- Argument `one`: every call names one span twice.
- Argument `two`: every call names a span of `left` and a span of `right`, two different owners, so
  no `assert_disjoint` is needed ([SIMD-3] (b)).

| program | what it models |
|---|---|
| `plain_samevar` | Careful C: one function with plain pointers, since some calls pass one span twice. |
| `plain_samevar_noalias` | `restrict` on both, valid for `two` only. It refuses `one`, which would be undefined behaviour. |
| `model_samevar` | `two` uses the normal copy: both spans noalias, each passed as its two words (inside a package the body is seen never to re-point them), with the [OPT-2] entry test. `one` uses `blend__one(s)`: one name, noalias, and no entry test, since `src.len()` is `dst.len()`. Every span made is range-checked ([TYP-31]). |
| `salvage_samevar_generic` | `one` goes to a copy with no noalias (salvage C). |
| `rust_samevar` | Rust refuses `&mut x` twice (E0499), so the idiom writes `blend_one` by hand. `blend` takes two `&mut [f32]`. Slicing checks each range, as the model does. |

**Assembly facts (clang -O2):**
- `plain_samevar`'s `blend` has a vector loop behind a run-time overlap test. With `dst == src` the
  test fails every time, so every `one` call runs the scalar loop (12 `mulss`/`mulps` in all).
- `blend__one` is a clean vector loop (`mulps`/`addps`, 8 floats per iteration).

**Prediction:** on `one`, the model is faster than plain C. Plain C's only way to serve both kinds of
call is to give up noalias. On `two`, it is plain C with `restrict`, which run 2 measured at 1.00 to
1.13x of the non-`restrict` version for an unknown length.

**As fast as C:**
- `model one` at or below `plain one`;
- `model two` within 5% of `plain_noalias two`.

**Falls short:** `model one` above `plain one`. That could only come from the span checks, since the
copy itself has nothing extra.

### Code size: `samevar_size.c`

Compiled only (`-c -ffunction-sections`). The bytes are read with `llvm-objdump -h -t`; that reads the
object and runs nothing. These numbers are measured.

| function | the grouping of its names | bytes of code |
|---|---|---|
| `blend` (normal copy) | `dst`, `src` | 508 |
| `blend__one` | `dst = src` | 247 |
| `mix4` (normal copy) | `a`, `b`, `c`, `d` | 719 |
| six copies with one pair merged (`ab_c_d`, `a_bc_d`, ...) | three names | 609 to 612 each |
| seven copies with two names left (`ab_cd`, `abc_d`, ...) | two names | 512 to 534 each |
| `mix4__abcd` | one name | 223 |
| **all 15 copies of `mix4`** | | **8,324** (11.6x the normal copy) |

**The bound.**
- A function needs one copy per grouping of its same-type `ref mut` parameters that some call
  actually uses. A module variable the function uses by name counts as one more name.
- The worst case is the product, over its types, of the Bell numbers B(k): 2, 5, 15 and 52 for
  k = 2, 3, 4 and 5 same-type names.
- A copy's own calls can need copies of their callees, so a program's total is bounded by the sum
  over functions of that product. In practice it is bounded by the call sites that name one whole
  variable twice, which are rare. Each such call site costs one copy, about 250 to 600 bytes here.
- Nothing runs while the program runs. Today's cost-table row ("one more copy of its code and nothing
  while running") holds, with these byte counts.

### Salvage

**C, `generic`:** cap the copies at two per function: the normal noalias copy, plus one copy with no
noalias at all, used by every call that names one variable more than once.
- That copy is correct for every grouping, because it assumes nothing about two names differing, so
  it is safe with every check still in place.
- Cost: those calls run at plain C's speed (`plain_samevar one`) instead of the one-name copy's.
- Use it when a function would need more than one merged copy (a compiler limit), and keep verdict
  88's copy for the common single pair.

### Memory

Two static 16 KB pools; every program is at the floor. Code size is the table above.

## 3. A `ref mut` span the callee may point elsewhere (R4, R6; run4/v5/area-A.md near line 2507)

### The question

`ref mut pos: MutSpan[f32]` may write the elements and may also point the caller's span elsewhere.
Across a package's edge the caller cannot see the body, so the span is passed by its address. After
the call, the caller must:
- read its span's pointer and length again;
- and lose what it knew of them (the start, and that the length is 16).

What does the caller pay?

### The program: `respan`

- 4,096 positions in chunks of 16.
- For each chunk, the caller calls the other package's `integrate(ref mut chunk, vel_chunk, 0.01)`,
  then walks the chunk itself and wraps each position into [-1000, 1000].
- 117,188 frames of 256 chunks.
- The other package is `pkg_respan.c`, a separate object with no link-time optimisation, so its
  bodies are unseen, as across a real package edge.
- Every callee runs the same `integrate_body`:
  - `pos`'s elements are noalias through a helper's `restrict` parameter, which clang keeps as alias
    scopes when it inlines (a `restrict` local would be ignored);
  - it has the [OPT-2] entry test on `vel`.
- So the variants differ only in how the span is passed.

| program | what it models |
|---|---|
| `plain_respan` | C passes the pointer and the length by value. |
| `model_respan` | The rule as written across a package's edge: `s` lives in memory, the call gets `&s`, and `s.ptr` and `s.len` are read back after it. Every span made is range-checked ([TYP-31]). |
| `model_respan_words` | The same program with `integrate` declared `const ref mut pos` (verdict 42), or called inside its own package: two words, and the caller keeps them. |
| `salvage_respan_flag` | Salvage D. |
| `rust_respan repoint` / `plain` | `&mut &mut [f32]`, Rust's re-pointable slice, against the idiom `&mut [f32]`. The callee is called through a `black_box`'d function pointer, so the call is indirect here and direct in C. |
| `*_rtlen` (C) | The chunk length is read from a volatile, so it is not known when compiling. This isolates the two reloads from the lost constant. |

**Assembly facts:**
- After the call, `plain`, `words` and `flag` (when the flag is 0) wrap the chunk in straight-line
  code: four 4-wide SSE groups, with no loop.
- `model_respan` reloads `len` and `ptr` from its stack frame, tests the length, and runs a generic
  8-wide loop with a remainder loop.

### What would count as "as fast as C"

- **As fast as C:** `model_respan` within 5% of `plain_respan`.
- **Falls short:** more than that. `model_respan_words` shows what verdict 42's `const` buys back, and
  `model_respan_rtlen` / `plain_respan_rtlen` show how much of the cost is the reload alone.

### Salvage

**D, `flag`:** keep passing by address, and have the callee return one flag in a register: 1 if any
of its lines re-pointed `pos`, else 0. On 0 the caller keeps its own words, with their known length;
on 1 it reads them back, as the model does.
- Safety: the flag is written by the callee's own compiled code. Every `pos = ...` line sets it, and
  every return path returns it. It is part of the function's calling convention, recorded in the
  package's interface file (R17).
- R6 still decides, when compiling, what a callee may point the span at.
- On 1 the caller does exactly what the model does.

Also not new but measured: `model_respan_words`. Verdict 42's `const ref mut`, or the same-package
fact, already removes the cost wherever the program writes it.

### Memory

Two static 16 KB arrays. Every C program is at the floor, and `rust_respan` adds two 16 KB `Vec`s.

## 4. The checked trampoline: the thread compare and the used-up mark (R15, R16; [FFI-53], [FFI-22], [FFI-33b])

### The question

The cost table cites 1.02x to 1.05x for the checked trampoline, against today's 1.47x
(`run3/combined-v4.md` line 549, AN-78). It says the release profile adds "one compare of the thread
per such callback, not measured".

**Finding, before any timing:** run 3's 1.02 to 1.05x already includes the creator-thread compare.
The models it cites all compare `s->creator` with a thread-local id:
- `artifacts/redesign2/threads/bench/ffi.c` model 2, measured at 1.03x;
- `attack/bench/ffi2.c` model 8;
- `attack2/bench/ffi3.c` model 10.

What those models lacked:
- [FFI-22]'s attach check. Their argument was that the creator compare proves the thread is attached,
  so the attach can be dropped. [FFI-53] as written does not say so: "every exported function and
  trampoline first attaches".
- The [TYP-8] check in the body.
- [FFI-53]'s stop on a stale call: run 3's models returned quietly. The stop is cold-path only.

So the row's "not measured" thread compare was measured. What was never measured is the rule as now
written: an inline attach check plus the thread compare.

### The runtime modelled (`cb_rt.h`)

- **The handle.** C holds a tagged number: the slot in the low 48 bits, and the generation (never 0)
  in the top 16 bits.
- **The table.**
  - Slots are 32 bytes: `{generation | type << 16}`, the creator, flags, and two words of state.
  - The table is reserved once and never moves.
  - Its base and length are non-static globals, so the compiler must load them, as it loads the
    runtime's own.
- **Registration.** Take a free slot, set the generation, type, creator and state, and hand C the
  tagged number.
- **End of a registration** (token ended, borrowed call returned, or a once callback called): move to
  the next generation. At 0xFFFF the slot is retired ([FFI-53]: one compare per registration).
- **Every trampoline call:**
  1. attach: a thread-local generation compared with the global one ([FFI-22]);
  2. the slot is inside the table;
  3. generation and type, in one 64-bit compare;
  4. the creator thread, compared with the thread-local number ([FFI-53], [FFI-33b]).

  Then the body runs. Every failure goes to an out-of-line stop, with [FFI-53]'s texts.

| mode | the hot path's checks (assembly of `tramp_add_point`, clang -O2) |
|---|---|
| model (rule as written, release) | attach (5 loads: `_tls_index`, gs:[0x58], the TLS block, the variable, the global; 1 compare); range (1 load, 1 compare); table base (1 load); generation and type (1 compare with memory); creator (1 load from the slot, 4 for the TLS variable, 1 compare); body (+1 `jo`) |
| `-DNO_THREAD_CHECK` (today's release) | the same without the creator line |
| salvage `fold` | no attach; the creator compare stands for it |
| salvage `teb` | no attach; the creator compare is `cmpl %gs:72, %eax`: one load |

### The programs

**`cb_event`** is the callback workload run 3 cites (run 2's `ffi.c`), kept for comparability: a C `fire(cb, ud, n)` calls the callback
200,000,000 times, and the body adds a point to the game. AN-78's v5 program uses
`register_cb(fn() shares mut game: game.add_point())`, with `callback(retained)` and `threads(creator)`.

| program | what it models |
|---|---|
| `plain_cb_event` | `ud` is the `Game*` (run 2's `ffi-0`) |
| `model_cb_event` | the rule as written (above) |
| `model_cb_event_nothread` | without the release thread compare |
| `salvage_cb_event_fold` | salvage E |
| `salvage_cb_event_teb` | salvage F |
| `rust_cb_event` | run 2's raw-pointer workaround (`ffi.rs`), which checks nothing |

**`cb_parse`** is the callback-heavy workload the row asks for. A C parser in the style of SAX or
libcsv, `csv_parse(text, n, on_field, field_ud, on_row, row_ud)`:
- walks 11,777,043 bytes of comma-separated numbers 10 times;
- calls back 20,000,000 times per field and 2,500,000 times per row.

Two `callback(borrowed)` callbacks with `threads(creator)` change two different real variables, so R4
allows them in one call. Per call of the parser, both are registered and ended. The same six programs
as `cb_event`. In `rust_cb_parse` the "C library" is written in Rust (no cargo to link a C object), so
its parse loop is rustc's.

**`cb_once`** tests the used-up mark:
- a C queue: `lib_request(cb, ud)`, then `lib_pump()` runs each queued callback once;
- 48,828 batches of 1,024 requests;
- each callback is `fn() copy of id: TOTAL += id`, with `callback(once)` and `threads(creator)`.

| program | what it models |
|---|---|
| `plain_cb_once` | each request's `{id}` from a free list, returned to it in the callback (no `malloc`) |
| `model_cb_once` | registration per request (slot, state in the slot); the trampoline as above, then the used-up mark tested and set, the body, and the registration ended; `TOTAL` is a module variable |
| `model_cb_once_nothread` | without the thread compare |
| `salvage_cb_once_genmark` | salvage G |
| `salvage_cb_once_nomark` | salvage H |
| `rust_cb_once` | the Rust idiom: `Box::into_raw` of the closure, and `Box::from_raw` in the trampoline. One allocation and one free per request; a second call would free twice. |

### Why the comparison is fair

- Same C library code in every C program (`cb_parse_lib.h`, `cb_once_lib.h`).
- Callbacks read from volatiles, so no program can see through the call.
- Same body; same calls.
- The model's extra stores (registration, ending) are the rule's.
- Plain C's `cb_once` free list is the careful C equivalent of the slot table's free list.

### What would count as "as fast as C" and as "falls short"

- **The row's cost of the release thread compare** is `model / model_nothread`.
  - As cheap as the table says ("one compare"): within 2 to 3%.
  - Falls short: more. The two TLS lookups (attach, then creator) do not share their gs:88 and
    `_tls_index` loads in clang's output.
- **The trampoline as a whole** is `model / plain`. Against the cited 1.02 to 1.05x:
  - within that range: holds;
  - above it: the attach check, or the body's overflow check, is the difference (`fold` removes the
    first).
- **The used-up mark** is `model_cb_once / salvage_cb_once_nomark`.

### Salvage

- **E, `fold` (attach folded into the thread compare).** The creator compare uses the thread-local
  number set at attach. An equal number proves this thread is the creator and is attached, provided:
  1. detaching clears the thread's number;
  2. the runtime ending (which bumps [FFI-22]'s global generation) ends every slot first.

  A mismatch takes the cold path, which attaches and compares again before stopping. Safety: every
  call that passes the fold passes both checks it replaces, and every call that fails it is attached
  and checked exactly as the model checks it. Run 2 measured this form at 1.03x.
- **F, `teb` (the OS thread id from the thread's own block).** Compare the creator with gs:[0x48],
  which is what `GetCurrentThreadId` reads: one load, against four for a `__declspec(thread)`
  variable in an executable (`_tls_index`, gs:[0x58], the module's TLS block, then the variable). It stands for attach too.
  - Safety needs one more runtime duty: an OS id is unique only among live threads, so when a thread
    ends (its TLS callback) or detaches, the runtime ends every `threads(creator)` slot that thread
    made. Those slots could never legally run again anyway. A later thread that reuses the id then
    finds no slot naming it.
  - Not covered: `TerminateThread`, which runs no callback.
  - On Linux the same idea uses the thread pointer (fs:0).
  - This is the "thread id cached where the trampoline compares it" idea, taken to the cheapest
    source.
- **G, `genmark` (the used-up mark inside the compared word).** Instead of testing and setting a
  separate flag (a load, a branch, a store), set one bit in the `{generation, type}` word just
  compared: one store, no test. A second call during the first fails the one compare, and the cold
  path sees the bit and gives the once message. After the call the registration ends, as before.
  Safety: the bit is set exactly when the model's flag is, and the compare already runs.
- **H, `nomark` (the mark proved unneeded).** A second call of a once callback can come only:
  - (a) while its one call runs, which on the creator thread needs the body to call into C (another
    thread fails the creator compare first);
  - or (b) after it, which the generation compare stops; the cold path names the once case from
    the slot's previous generation.

  R5 already knows every call a body makes, and `TOTAL += id` makes no foreign call. So for a
  `threads(creator)` or `threads(main)` once callback whose body calls no C, the mark goes: nothing
  per call. Safety: each way a second call can happen is still stopped by a check that remains, or
  cannot happen. A body that may call C, or a `threads(any)` callback, keeps the mark (model or G).

### Memory

- **cb_event:** floor; the table is 64 x 32 B.
- **cb_parse:** floor + the text: 14,000,000 B reserved, 11,777,043 B touched, in every program
  (Rust's `Vec` likewise); the model's table adds 2 KB.
- **cb_once:**
  - plain: 16 KB of `Ctx` and a 16 KB queue;
  - model: + 1,088 x 32 B of table + 4.4 KB of free list;
  - Rust: at most 1,024 live 8-byte boxes (heap-rounded) + the queue.

  All within about 100 KB of the floor.

## Open doubts

1. **The 1.02 to 1.05x already contained the thread compare** (section 4). The cost-table row and
   [FFI-53]'s last sentence ("and, in the release profile, one compare of the thread") count it as
   extra. The new numbers settle what the rule as written costs with [FFI-22]'s attach included.
   Whether the fold (E) may replace the attach is a rule question for the lead.
2. **TBAA hides the `this` question under clang.** The cost depends on the C compiler: clang's
   struct-path alias analysis already separates `Player::hp` from `Game::damage`, and MSVC has none.
   The lead's `cl` build of the `this_*` programs is the stricter test.
3. **Floats in the checksums.** The float checksums (`this_mix`, `samevar`, `respan`) assume no FMA
   contraction. That holds for clang and rustc on baseline x86-64 and for `cl` without `/arch:AVX2`.
   An AVX2 build could print different checksums with correct code.
4. **`rust_cb_parse` uses rustc's parse loop**, not clang's. Compare its callback overhead only
   through the other programs.
5. **Ember's real slicing syntax** for a sub-span (`left[a .. a + n].as_mut_span()`) is written as the
   rules' examples suggest. The C is what matters: one range check per span made.
