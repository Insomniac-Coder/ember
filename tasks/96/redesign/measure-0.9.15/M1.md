# M1: owner counts, the `thread_shared` view count, and a handler's hold on its own state

Agent M1, spec 0.9.15_Hardened_1. My job covers three rows of the cost table in section 2 of
`tasks/96/redesign/run4/v5/rules.md`:

1. "a count +1 / -1, and before each +1 one compare with the count's maximum" (R9, `[RC-1]`, `[RC-4]`,
   `[RT-7]`, `[RT-8]`, `[RT-10]`);
2. "one atomic count for the view's life" for a view of a `thread_shared` object opened from a `weakref`
   link (R10 point 2, `[RC-5]` point 2, `[WK-12]`);
3. "one count on a handler's own state" for a handler that removes itself and then uses its state (R12,
   AN-60).

Sources are in `tasks/96/redesign/measure-0.9.15/M1/`. Build lines are in `M1/build.txt`; the run list
with expected checksums is in `M1/runs.txt`. Every program built with `clang -O2` (LLVM 22.1.8) or
`rustc -C opt-level=2 --edition 2021` (1.98.1) into `target/measure-0.9.15/M1/bin/`: 23 C, 7 Rust.
`clang-cl /Zs /W3` and `clang -Wall -Wextra` gave no warnings. **No program was run.** The C avoids
GCC-only extensions so that MSVC can build it: atomics use the `<intrin.h>` Interlocked intrinsics,
`noinline` and `noreturn` are written as `__declspec`, `restrict` as `__restrict`, and overflow checks
have an MSVC path (`_mul128`). MSVC itself was not available to me.

Shared files: `harness.h` (copied unchanged), `harness.rs` (run 3's Rust twin from
`target/redesign3/10-area-C/bench/`, same LCG and same output line), and `m1rt.h` (the stop path,
atomics, run 3's slab allocator and portable checked arithmetic). Each workload's programs include one
body or variant header (`counts.h` + `retarget_body.h` / `hotshare_body.h`, `weakview.h`,
`selfremove_model.h`). So the programs of a workload are the same source and differ only in the
mechanism being measured.

## A finding first: run 3 already measured a compare

The cost table says the run 3 numbers (1.13x to 1.25x of plain C) were "measured without the compare".
That is wrong. In run 3's `target/redesign3/10-area-C/bench/share_c.c`, `MODEL 3`, the +1 is:

```c
static inline void retain(Player *o) { if (o->h.strong - 1u < UINT32_MAX - 1u) { o->h.strong += 1; return; } retain_slow(o); }
```

That is a two-sided range compare (a subtract, a compare and a branch). It goes to `retain_slow`,
which reports "count overflow", when the count is at `UINT32_MAX` and also when it is 0. So run 3's
1.13x to 1.25x already included a limit compare, slightly heavier than the one `[RT-7]` asks for. My
`model_retarget` uses the exact one-sided compare, and `diag_retarget_nocompare` has no compare, so the
compare's own cost can now be isolated.

## Workload 1: `retarget` (run 3's AN-52 (a) workload, unchanged)

**Question.** On re-pointed shared targets, what do the 0.9.15 owner count and its limit compare cost
against plain C, against a count with no compare, and against Rust's `Rc` and `Arc`? And the same for a
`thread_shared` count?

**Work.** This is run 3's `share_c.c` loop, unchanged, with seed 42:
- 262,144 players from one slab block, 1,048,576 watchers, 32 frames.
- Each step: `t.hp -= 1`, plus a multiply-add over the inventory length; one step in eight pushes to
  the inventory.
- One step in sixteen re-points the watcher at a random player:
  `ws[i].target = shares mut players[r]`, which is +1 on the new player and -1 on the old one.

Checksum **80363660820**, as run 3 printed.

| program | what it models |
|---|---|
| `plain_retarget` | run 3's `MODEL 0`: a raw pointer, a 32-byte player, no header, no count, no checks |
| `model_retarget` | the rule as written: an 8-byte header `{u32 count, u32 type index}` (`[OBJ-1]`). Before each +1 the count is compared with 4,294,967,295 and the program stops there (`[RC-1]`, `[RT-7]`, R9). The -1 is a plain subtract with a test for zero, and the end is out of line (`[RT-8]`, `[RT-10]`). There is a bounds check on `players[r]`, as today. The view `t = ref mut ws[i].target` is not counted (`[RC-2b]`, `[RC-5]` point 1). |
| `diag_retarget_nocompare` | the model without the limit compare, which is a C++ intrusive count. This is the baseline of `[BEN-6]`'s gate ("`shares` owners <= 1.15x a C++ intrusive count"). |
| `model_retarget_ts` | `thread_shared Player` as written: +1 is one `lock xadd`, and the program stops when the returned value is 2,147,483,647 or more (`[RC-4]`, `[RT-7]`, `[RT-10]`); -1 is a `lock dec` (`[RT-8]`) |
| `diag_retarget_ts_nocompare` | the `thread_shared` model without the limit test (an atomic intrusive count, `[BEN-6]`'s `thread_shared` baseline) |
| `salvage_retarget_fold` | salvage 1 (below) |
| `salvage_retarget_wide` | salvage 2 |
| `salvage_retarget_ts_wide` | salvage 3 |
| `rust_retarget_rc` | run 3's `share_cell.rs`, unchanged: `Rc<Player>` with `Cell`/`RefCell`. `Rc::clone` checks its add for wrap-around and aborts. |
| `rust_retarget_arc` | the same program with `Arc`: one `fetch_add`, with its result tested against `isize::MAX` |

**Fairness.**
- All C programs do identical work in the same order from one source.
- The players have the same layout: 32 bytes for plain C and 40 bytes with the header. The only
  exception is `wide`, which keeps 40 bytes because the header is still 8.
- The `_ts` programs keep changing `hp` and the inventory directly. `[RC-7]` / E7014 refuse that for a
  `thread_shared` value, but keeping the body identical isolates the count. The lock a real program
  would take is costed by the "a lock" row.
- The Rust programs allocate each player separately (`Rc::new`), as run 3 did. That is Rust's idiom,
  and it is why their memory is higher.

**Reading the results.**
- **The compare is free** if `model_retarget / diag_retarget_nocompare` is within noise (about 1.02 or
  less). The count itself is not this row's question: run 3 measured it, and it is mostly the cache
  miss on a random player's header.
- **The rule falls short** if:
  - that ratio exceeds about 1.05; or
  - `model_retarget` exceeds `[BEN-6]`'s 1.15 x `diag_retarget_nocompare`; or
  - `model_retarget` is slower than `rust_retarget_rc`.
- Each `_ts` program is judged the same way against `diag_retarget_ts_nocompare` and
  `rust_retarget_arc`.

**Memory** (run 3's measurements for the same layouts):
- plain C: 53,284 KB.
- every 40-byte-player program: about 55,332 KB. The 8-byte header adds 262,144 x 8 B = 2 MB. `wide`
  and `_ts` add nothing more.
- `rust_retarget_rc`: about 61,920 KB, and `_arc` the same, because each player is in its own heap
  block with a 16-byte `RcBox` header.
- A compare costs no memory.

## Workload 2: `hotshare` (the compare's worst case)

**Question.** In `retarget`, the +1 sits behind a cache miss on a random player's header in one step
of sixteen, so the compare can hide in that latency. What does the compare cost when owner making and
ending is most of the work and everything stays in the cache?

**Work.** 1,024 players (x = position), 4,096 watchers, 20,000 frames. Every step:
`t = players[(3i + f) & 1023]`, then `ws[i].target = shares mut t` (+1 on `t`, -1 on the old
target), then `acc += t.x`. That is 81,920,000 re-points.

**Checksum 41,904,175,104**, worked out by hand:
- 3 is odd, so `(3i + f) & 1023` takes each value 0..1023 four times as `i` runs over 0..4095.
- So each frame adds 4 x (0 + ... + 1023) = 2,095,104. The final pass over the watchers adds the same
  amount once more.
- Total: 20,001 x 2,095,104 = 41,904,175,104.
- Checked with awk.

The programs are the same nine as `retarget` (from the same `counts.h`), plus `rust_hotshare_rc` and
`rust_hotshare_arc`.

The body only reads `x`, so here the `thread_shared` programs are faithful as they stand.

What clang emitted for the inner loop (`clang -S`):

| program | +1 | -1 |
|---|---|---|
| plain | none | none |
| model | `mov; cmp $-1; je; inc; mov` | `decl (mem); jne` |
| fold | `mov; inc; je; mov` (the add and branch fuse) | `decl (mem); jne` |
| wide | `addq $0x80000, (mem)` | `subq $0x80000, (mem); jae` |
| ts | `lock xaddl; cmp $0x7FFFFFFF; jae` | `lock decl; jne` |

Note that the wide salvage's +1 and -1 are the same number of instructions as an unchecked 32-bit
count.

**Reading the results.**
- `model_hotshare / diag_hotshare_nocompare` gives the compare's real upper bound.
- `model_hotshare / plain_hotshare` gives the whole cost of counting.
- `model_hotshare_ts / diag_hotshare_ts_nocompare` should be about 1.00, because a `cmp`/`jae` after a
  `lock xadd` hides in the locked instruction's latency. That is the claim to confirm.
- Against Rust: `rust_hotshare_rc` is Rc's clone and drop with Rust's own check;
  `rust_hotshare_arc` is the same with Arc.
- **"As fast as C"** here means the model is within `[BEN-6]`'s 1.15x of the intrusive count and not
  slower than Rust's `Rc`. No counted program can match `plain_hotshare`: the counting is the work.

**Memory.** The data is about 40 KB of players, 8 KB of pointers and 32 KB of watchers. Every C
program's peak should be the process's base working set, within about 10 KB of each other. Rust adds
1,024 separate heap blocks of about 64 bytes each.

## Workload 3: `weakview` (R10 point 2: a view of a `thread_shared` object through a `weakref` link)

**Question.** What does the one atomic count a view holds for its life cost? It is a compare-exchange
loop to open, plus an atomic subtract when the view ends. Compare it with:
- plain C;
- the same Ember program on one thread (R11: a header test only);
- Rust's `Weak::upgrade` plus the drop of the `Arc` it gives.

**Work** (the Ember program is written out in `weakview.h`):
- 16,384 slots of `thread_shared Player` and 1,048,576 cameras. Each camera has a
  `target: weakref Player` following slot `s(i) = (i * 40503) & 16383`.
- 64 frames. Each frame first replaces 256 players: the slots `j = f (mod 64)`. Their owners end, so
  the players end.
- Then every camera opens its link. If the player lives, `acc += p.x`. If it has ended, the camera
  re-points: `cams[i].target = weakref players[s]`, which is weak +1 / -1.
- That is 67,108,864 openings, of which 1,048,576 find the player ended.

**Checksum 33,790,885,888**, worked out by hand:
- Each slot has 64 cameras.
- Frame `f` adds 528,482,304 - 16,384 (f mod 64).
- The failures add 1,048,576.
- The derivation is in `weakview.h`, and I checked it with a brute-force awk sum.

| program | what it models |
|---|---|
| `plain_weakview` | what a careful C game programmer writes: players inline in slots with a generation number. A camera keeps `{slot, gen}`, and opening compares generations. Ending a player bumps the generation and reuses the slot in place. No allocation, no counts. |
| `model_weakview` | the rule as written. A 12-byte header `{count, type index, weak count}` (`[OBJ-1]`) on a 32-byte block from the slab. Opening (`[WK-12]`, `[RT-10]`): a null test (`[WK-11]`: a link may hold nothing), then a compare-exchange loop that raises the count only while it is above zero, with the 2,147,483,647 limit test (`[RC-4]`). The view gives the count back with an atomic subtract (`[RC-5]` point 2, `[RT-8]`). Re-pointing is atomic weak +1 with the limit test and weak -1 (`[WK-11]`, `[RC-4]`). There is a bounds check on `players[s]`, as today. |
| `model_weakview_onethread` | the same program with one-thread players (R11). Opening is a null test and one header test (`[WK-12]`); the view has no count (R10 point 1). Weak +1 is compared with 4,294,967,295. A one-owner player is not counted: ending it writes count 0. |
| `salvage_weakview_plaindata` | salvage 4 (below) |
| `rust_weakview_arc` | `Vec<Arc<Player>>` and `Vec<Weak<Player>>`. `upgrade` is a CAS loop with Arc's overflow check; the `Arc` it gives is dropped at the end of the match arm. |
| `rust_weakview_rc` | the same with `Rc`: the Rust twin of `model_weakview_onethread` |

**Fairness.**
- All Ember-layout programs share one source and run the same work in the same order.
- Plain C's layout differs on purpose. Inline generational slots are what C writes, and they are the
  real target.
- `model_weakview_onethread` and `rust_weakview_rc` separate R10 point 2's own cost (atomic count
  versus header test) from the layout's cost (blocks and pointers versus inline slots).
- Everything runs on one thread, so the atomics are uncontended. This is the floor of point 2's cost
  (see the open doubts).

**Reading the results.**
- R10 point 2's own price is `model_weakview / model_weakview_onethread`.
- "Matches Rust" means `model_weakview` is no slower than `rust_weakview_arc`. Both do the same
  CAS plus subtract per opening.
- **The rule falls short** if `model_weakview` is slower than `rust_weakview_arc`, or if the salvage
  closes most of the gap to `onethread` (it costs nothing in memory).

**Memory** (expected; nothing was run):
- Every program has the cameras: 8,192 KB, 8 bytes each (a pointer, or plain C's `{slot, gen}`).
- Plain C adds 384 KB of slots.
- The Ember programs add a 128 KB pointer list plus 16,384 x 32 B = 512 KB of blocks. That is five
  128 KB slab chunks, because up to 256 ended blocks stay alive until their 64 cameras re-point,
  within the same frame. So about 0.3 MB more than plain C.
- Rust is about the same as Ember: 32-byte `ArcInner` blocks from the system heap, with its overhead.

## Workload 4: `selfremove` (R12: a handler that removes itself and then uses its state)

**Question.** What does the one count held on a handler's state across its own removal cost? R12 and
AN-60 call it a rare path.

**Work.** This is run 3's W4, repeated 8 times in one process because one repetition takes about
25 ms:
- 10,000 handlers and 10,000,000 dispatches per repetition.
- 100 handlers per repetition remove themselves, register a replacement, and then read their own
  `counter`.
- Each repetition frees everything it made.

**Checksum 279,575,944,000** (8 x run 3's 34,946,993,000).

| program | what it models |
|---|---|
| `plain_selfremove` | run 3's plain C baseline (`target/redesign2/bench/w4.c`, the `plain_w4` of `RUN3/26-timer.md`). It uses one malloc per environment, and the handler frees its own environment as its last act. |
| `model_selfremove` | run 3's `model_w4_state_block` (`25-c-writer-fix/w4.c -DSTATE_BLOCK`), the layout 0.9.15 keeps: `owns counter` and `copy of m` in the state block, and `total` as main's real variable at its address. Tags: [M1] two words copied out per call; **[M2] one count, compared with its maximum, held across `d.unregister_current()`** (R12, AN-60, `[RT-7]`); [M3] removal ends the state; [M4] one slab block per handler. The checks are as in run 3 (bounds, zero divisor, overflow), rewritten portably. `ref mut d` / `mut self` are `__restrict` (R4). |
| `salvage_selfremove_hoist` | salvage 5 (below): the model with [M2] removed and nothing else changed |
| `rust_selfremove` | run 3's `rust_w4.rs` plus the repetition loop. Rust takes every closure out of its slot for each call (`Option::take`) and puts it back afterwards: the counterpart of [M2], paid on every call. |

**Fairness.** `model_selfremove` versus `salvage_selfremove_hoist` isolates [M2]: the two are the same
source with one `#ifdef`. Plain C uses a different allocator (malloc) and has no checks, as run 3's
baseline did.

**Reading the results.**
- [M2] runs 800 times in 80,000,000 calls, so `model / hoist` should be 1.00 within noise.
- If it is not, the count is somehow on the hot path. That would be a model defect, and it would also
  be the reason to adopt the hoist.
- The model against plain C should reproduce run 3's 1.091x. That gap is the checks and the slab, not
  [M2].

**Memory.** Run 3 measured `plain_w4` at 4,072 KB, `model_w4_state_block` at 4,264 KB and `rust_w4` at
4,476 KB. The repetitions free and reuse memory, so the peaks should match. [M2] adds no memory.

## Salvage variants and their safety arguments

**1. `fold`: the compare read from the increment's own result** (`salvage_retarget_fold`,
`salvage_hotshare_fold`).
- The code is `n = count + 1; if n == 0: stop; count = n`. `n == 0` holds exactly when the count was
  4,294,967,295.
- So it gives the same stop, at the same count, with the same message. The wrapped value is never
  stored, because the store comes after the branch and the stop does not return.
- It is one thread (`shares` counts never cross threads, E7015), so nothing can observe the count
  between the add and the test.
- This is a codegen rule for `ember_rt.h`'s inline +1, not a spec change. Clang did not find it on
  its own: it emitted a separate `cmp $-1`.

**2. `wide`: owners minus one in the top 45 bits of a 64-bit header word, no compare**
(`salvage_retarget_wide`, `salvage_hotshare_wide`).
- Layout: the type index is in bits 0..18, and owners - 1 in bits 19..63. The header stays 8 bytes.
- A +1 is `add $2^19, (mem)`. A -1 is `sub $2^19, (mem); jb`, where the borrow means "that was the
  last owner". That is the same instruction count as an unchecked 32-bit count.

Safety argument:
- Safe Ember has no way to make an owner count unit without keeping the owner somewhere. `mem.forget`
  is gone (E1010). That is the reason Rust needs its check and Ember need not.
- Every unit of a count is a distinct live owner: a field, a list slot, a local, a function value's
  state, or a view's count (`[RC-5]` point 2), each held in its own 8-byte word or in a register.
- On x64 Windows, and on Linux with 4-level paging, user space is 2^47 bytes. So at most 2^44 owner
  words can exist, which is less than 2^45. The field cannot overflow, and no compare is needed.
- The one exception is `unsafe` `into_raw()`, which hands a count unit to C. That site, and only that
  site, keeps a compare.

Conditions the owner must rule on:
- The type index shrinks from 32 bits to 19 bits (524,288 class types), which changes `[OBJ-1]`.
- Targets with 57-bit address spaces (5-level paging) would need at least 55 count bits, so they would
  keep the 32-bit compare.
- `[TST-31]`'s `count_bits: 8` tests lose their purpose.
- The 12-byte header's weak count keeps its 32-bit compare. Alternatively the same trick could be used
  with a 16-byte header, which costs memory.

**3. `ts_wide`: the same word raised with one locked add, no limit test**
(`salvage_retarget_ts_wide`, `salvage_hotshare_ts_wide`).
- The bound in salvage 2 counts owners, and it holds whatever the number of threads. Threads racing
  between an add and a later check do not matter, because the count never comes near 2^45.
- So `[RC-4]`'s half-range trick and its result test both go.

**4. `plaindata`: no view count for a `thread_shared` class whose end frees nothing and runs nothing**
(`salvage_weakview_plaindata`).
- Opening becomes an atomic (acquire) load of the count and a test, with no read-modify-write.

Condition, checked when compiling:
- The class family has no `drop`.
- No field owns memory or holds a link. Only scalars, inline structs of scalars, and `Atomic` fields
  are allowed. A `weakref` field is excluded, because its end gives back a weak count on another
  object.
- The link the view was opened from is not re-pointed or ended in the view's life. This is the same
  kind of check as R10 point 1. Where it fails, the view keeps the count as written.

Safety argument:
- (a) The block cannot be freed during the view. The link the view was opened from holds a weak unit,
  and that unit keeps the block.
- (b) Another thread may end the object during the view. But ending this kind of object changes no
  byte the view reads: no drop runs, nothing is freed, and only the count word changes. A
  `thread_shared` field is never written directly (E7014). So every read returns a value the object
  held while it lived. That is exactly what the view would read if the end came after the view, which
  is the order Rust's upgrade imposes.
- (c) The acquire load orders the field reads after the liveness test.

What changes: nothing observable, because the end runs nothing. The memory is unchanged too, because
the block was kept anyway.

The general form, for classes that do have a drop, is epoch-based deferral (as in RCU or
crossbeam-epoch). The end marks the count 0 at once, and the drop and free wait until every thread
passes a point where it holds no view. The cost is one store per thread per such point, plus the
memory of the objects ended in the last two epochs. I did not write this form.

**5. `hoist`: no hold count on a handler's own state** (`salvage_selfremove_hoist`).
- Condition, from the call's code (R5): every use of the state after the call is a read of a field
  the call cannot change. Here `unregister_current`, `register` and `make_handler` change only
  `d.handlers`.
- Then the reads move above the call. The state can end inside the call, and nothing reads it
  afterwards.
- The state then ends where the source removes the function value, which is its last owner (`[RC-3]`:
  "as the source says"), rather than at the end of the body.
- That earlier end is observable only if the state owns something with an effectful `drop`. In that
  case the compiler keeps [M2].
- On this rare path the gain is code size, not speed.
- A second option, not written: if a function value can never be shared, a state has at most two
  owners (its function value and the hold). Then [M2]'s compare is provably dead and only the plain
  +1/-1 remains.

## Not measured here

- The R12 C-callback case: a callback that ends its own token while it runs, which the trampoline's
  bookkeeping handles. It is a different row.
- Contended atomics (more than one thread), for both the `thread_shared` count and the view count.
- Ember's drops at the end of `main` in workloads 1 to 3. Like run 3, no program frees there, and
  Rust's drops run after `report`, outside the timed region.
