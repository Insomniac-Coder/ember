## 4. Technical points I settled, with reasons

1. **A function-type parameter is a function value; the template form is the direct one.** CLO-3 used
   to make `f: fn(A) -> R` an implicit generic. Now `fn(A) -> R` is one type wherever it is written,
   and a function that wants each function given compiled in takes it as a type parameter
   (`[F: fn(A) -> R]`, CLO-14). The reasons:
   - Verdict 38's question set the two forms apart by exactly this cost.
   - Area B's note 6 says a plain `f: fn()` counts every function the program can store there.
   - Agent 02's cost table in p10 says "a call through a function value (a parameter, ...): one
     indirect call".
2. **Where a function value's state lives** (CLO-10).
   - V5 has two words, `{code, state}`, and the state in the value's own block.
   - CLO-10 adds that a state of one word or less may sit in the state word itself.
   - Nothing a program can see changes. It keeps agent 01's PHIL-2 ("a function value whose state
     exceeds its inline capacity") true.
   - A function value with no state is `Copy`. One with state is not, and `=` hands it over, since its
     state is owned.
3. **The arena.** V5 does not mention `Arena`'s own `alloc*` methods. Today's ARN-1 rested on `self`
   and `mut self` receivers, which are gone. The new ARN-1 says four things:
   - `alloc*` moves the arena's cursor, so it is called through a name that may change the arena: a
     plain name never changes anything.
   - Each allocation gives memory that no earlier view of the arena reaches.
   - The views point into that memory, not into the cursor. So an allocation ends no earlier view and
     overlaps none: two fields are separate places, as in agent 01's BRW-4 and EXC-19.
   - `reset()`, `scope()` and the arena's end end every view into the arena.

   Two tasks allocating from one arena then change one place, which is E7007, with no extra rule. The
   example takes `ref mut frame: Arena`, as LT-44 allows.
4. **C14 widened safely.** The inventory's wording, "only `Allocator` methods", would also refuse an
   `Arena`'s `alloc*` and the making of other values while one value lives. ALC-5 allows everything that
   only allocates, since none of it touches a block already given out.
5. **The C14 message.** The inventory's message moved `reset` "below the last use". A value lives until
   it ends, not until its last use, and its end calls `deallocate`, so that fix could still be refused.
   The message now gives `mem.drop(names)` above the reset, which compiles (R18).
6. **The `Layout` check.** The constructor checks two things and panics `invalid Layout` otherwise:
   - `align` is a power of two;
   - `size`, rounded up to a multiple of `align`, fits an `isize` (as Rust's `Layout::from_size_align`).

   The fields are `pub(read)`, so no other `Layout` exists.
7. **C01's extent.** Only `deallocate` and `reallocate` are `unsafe`, as the crosswalk says. `allocate`
   frees nothing and gives a raw pointer, as Rust's `Allocator::allocate` does.
8. **C20's extent.** `uninit()`, `write` and `write_at` are all unsafe for a `T` that needs drop. That
   covers both readings in the inventory (L6 named the writes, F3 named `uninit()`).
9. **`check_disjoint`.** It returns `Result[void, void]`, as AN-14's `Ok(_)` and `Err(_)` branches need.
   Its `Ok` branch is a proof, as inside `if i != j:` (area A's note 1). The W2190 message offers it, so
   it must work.

   Today's `assert_disjoint_all` returned a `Result`, so it is renamed `check_disjoint_all`, and
   `assert_disjoint_all` is the stopping form. This is the same rename as for the two-view functions.
10. **DSJ-10.** Making a span and comparing two address ranges read no element (area A's note 2).
    Without this, `assert_disjoint`, which R4 names as a proof, could never be reached with a `ref mut`
    span, as in AN-14's `mix`. A read of an element through the other view before the proof stays
    E3021.
11. **E3095 kept.** Two single-object references given to `assert_disjoint` are E3095. V5 says nothing
    about it, so today's code stays.
12. **A map with two loop names gives its keys and values** (`for k, v in m:`, CTL-1). Verdict 95's
    `for k, ref mut v in counts:` implies it.
13. **`for v in xs.iter_mut(): v += 1` is E3023** (CTL-1). The vocabulary refuses it without a code. A
    plain loop name changes nothing (BRW-15), so E3023 is the code that already fits, and its help gives
    `for ref mut v in xs:`.
14. **Codes that moved to V5's meanings.**
    - Taking a class object's field out is E3013, not E3012.
    - A part handed over, then its owner used whole, is E3040, not E3042.
    - A `once` function given where a function may run twice is E3013, not E3030.

    V5 section 4 gives these cases to E3013 and E3040.
15. **CLO-7 kept, CLO-15 removed.** CLO-7's subject, library functions that keep a function or run it on
    another thread, still exists, so it keeps its ID with the new text: `owns`, `thread_shared fn()`,
    capture words. CLO-15's subject, a capture rule decided by the call, is gone.
16. **E2229 has no case left** (CORO-12):
    - `mut self` is gone.
    - A generator's `for` walks by position (AN-77).
    - A `gen fn` method's views of its object are views like a parameter's.
17. **`Cell` is kept, and `RefCell` is removed** (see the request to the lead below).
18. **MOD-9 is short.** Agent 02's EFF-4 already carries R17 in full. MOD-9 says the same thing for a
    package and cites EFF-4.
19. **No duplicate call rules.** BRW-11, BRW-21, BRW-22 and LT-47 (agent 01) and GRM-41 (agent 03)
    already carried R4's overlap rule, the call check, noalias, the view put in through `ref mut`, and
    the first line. FN-1 and FN-2a cite them instead of repeating them in new FN rules.
