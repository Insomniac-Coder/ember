### G5-1 — drop(mut self) runs with no whole-object write: a view taken in drop is freed under it (use-after-free) — **fixed, D-453**

Kind: bug. Severity: high. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** g5-locking\q25_drop_uaf_visible.em: in drop, v = self.items[..]; self.reset() (reset: self.items = [0]); then 64 fresh 8-int arrays are allocated; println(v) prints [55, 55, 55, 55, 55, 55, 55, 55] (release). v viewed [1..8] and now reads another array's memory. In q22_drop_view_alias_write_checked.em the reset write check is kept (ember_field_check_write in em_Bag_reset) and still passes: it prints [0], then [1, 2, 3, 4, 5, 6, 7, 8] from the freed buffer. In q20 the [EXC-3] pass removed reset's check outright. The same shape in an ordinary mut self method (q21) panics correctly. Cause: c0c7beb deleted the callee-entry BeginAccess in lower.rs build() and moved the write to callers, but the runtime-called drop has no caller. ember_rt.c:960-961 calls ti->drop(object), and the adapter from codegen lib.rs:1756-1785 calls em_Bag_drop(&handle) with no ember_object_begin_write. Inside drop, borrows.rs:1154-1158 (body.mut_self) treats self's fields as covered: the emitted em_Bag_drop has 0 field or object access calls.

**Why it is wrong.** [EXC-15]: a mut self method (drop is one) holds a write access to every field from entry to return, and accesses to self inside are covered by it. Here nothing holds that write, so the covered view protects nothing and a write through self passed on succeeds. This is a regression from moving the whole-object write to callers.

**Suggested fix (not applied).** Bracket every runtime drop call (the adapter, including the base-class drops it chains) with ember_object_begin_write/end_write over the dynamic class. Make it visible to remove_never_firing_checks_all (access.rs:316) as a held whole-object write, for example by modelling the drop call in MIR or by treating any class with a user drop as having a held object write.

**Checker's evidence.** Reran review2\g5-locking-verify\q25_drop_uaf_visible.em: it printed '8' then '[55, 55, 55, 55, 55, 55, 55, 55] 64'. The view v of [1..8] taken in drop now reads another array's memory. q22_drop_view_alias_write_checked.em printed 8, 8, [0], [1, 2, 3, 4, 5, 6, 7, 8]: the freed buffer is read. In the emitted C (q22.c), em_Bag_drop_adapter is only `em_obj_Bag* handle = raw; em_Bag_drop(&handle);` with no ember_object_begin_write. em_Bag_reset keeps ember_field_check_write(&_1->_access_items, ...) at line 11, and that check passes because nothing marks the word. The control q21 (the same body in an ordinary mut self method called from main) panics: 'write access to Bag.items while a write access to Bag.items is active; active write ... began at 19:5'. Spec [DRP-1] says `fn drop(mut self)`. [EXC-15] says a mut self method holds a write to every field from entry to return. So this is a real soundness hole.

**Checker's notes.** Kind: bug (use-after-free), high severity. I did not separately check the base-class drop chaining in ember_rt.c, but the plain case alone is enough.

### G5-2 — A mutable view inside Option or a tuple, returned through an interface or virtual call, carries only a read access (use-after-free) — **fixed, D-452**

Kind: bug. Severity: high. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** g5-locking\q62_interface_option_ref_mut_uaf.em: interface Slots: fn slot(mut self, i) -> Option[ref mut String]. Through h: Slots: r = h.slot(0); s = c.items[0].as_str() (another handle); write 'replacement' through the ref mut; allocate; println(s) prints XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX (release) instead of the original text, so s reads freed memory. q60 (same shape over int) reads len(c.items) while the ref mut lives with no panic. The direct-call control q61 panics correctly: 'read access to Bag.items while a write access to Bag.items is active'. Cause: borrows.rs:429-433 in call_result_accesses (FuncRef::Virtual | Interface) sets mutable only for a top-level Span{mutable} or Ref{mutable}, while is_view (types lib.rs:1669) admits Option, tuples and structs. Direct calls use the callee's per-field summary and are right.

**Why it is wrong.** [EXC-18]: the access that ref mut h.f begins is a write and is carried to the caller until the loan dies. As a read, [EXC-2] lets a view of the same field begin, and the write through the ref mut then frees what that view points into.

**Suggested fix (not applied).** Derive mutability from the whole result type: true if any view reachable in it is mutable, using the same walk as is_view. Better, carry a per-slot summary as the direct path does.

**Checker's evidence.** Reran q62_interface_option_ref_mut_uaf.em: it printed 'XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX' where s = c.items[0].as_str() should show the original text, so s reads freed and reused memory. borrows.rs:429-433 in the FuncRef::Virtual|Interface arm sets `mutable` only when the result type is TyKind::Span{mutable:true} or TyKind::Ref{mutable:true}. That arm is entered whenever types.is_view(dest) holds, so an Option[ref mut String] result gets a read access (mutable=false). Control q61 (direct call, Option[ref mut int]) panics correctly: 'read access to Bag.items while a write access to Bag.items is active'. q61 is a plain self method over int, not the exact mirror of q62, but the direct path's per-field summary is what makes it panic.

**Checker's notes.** Kind: bug, high severity.

### G5-3 — Calling any mut self method that returns a view or ref of a field always panics — **fixed, D-451**

Kind: bug. Severity: high. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** g5-locking\q33_mut_self_view_getter_legal.em (one handle, fn sorted_view(mut self) -> Span[int]; v = b.sorted_view(); println(v)) gives: panic at q33...:14:9: exclusivity violation: read access to Bag.items while a write access to Bag.items is active; active write began at 14:9. It does the same in release. q32_ref_mut_getter_legal.em (fn slot(mut self, i) -> ref mut int) panics with 'write access ... while a write access ... is active'. Emitted C for q32: ember_object_begin_write(_1); _2 = em_Bag_slot(_5, 0); ember_field_begin_write(&_1->_access_items ...); ember_object_end_write(_1). The carried access begins before the call's own whole-object write ends. Cause: lower.rs:2008 (also 1922 and 2081) pushes the mut-self EndAccess as the first statement of the call's next block, and borrows.rs:882-890 inserts the carried access at Point{block: next, index: 0}, which is before that statement.

**Why it is wrong.** [LT-1] rule 1 lets a mut self method return a view of its receiver, and [EXC-18] carries the access to the caller once the call ends. The call's whole-object write lasts only for the call ([EXC-15], VIII.3 table). D-218's fix covers plain self getters only; every mut self getter is unusable.

**Suggested fix (not applied).** Begin carried result accesses after the call's own EndAccess statements in next, for example by inserting after the leading EndAccess run, or by having push_events order ends from both sources before any begin. Add an EXC-18 test with a mut self getter.

**Checker's evidence.** q33_mut_self_view_getter_legal.em (one handle, fn sorted_view(mut self) -> Span[int]) panics: 'q33...:14:9: exclusivity violation: read access to Bag.items while a write access to Bag.items is active; active write of Bag.items began at q33...:14:9'. q32_ref_mut_getter_legal.em panics: 'write access to Bag.items while a write access to Bag.items is active ... began at 14:16'. The emitted em_main for q32 runs, in order: ember_object_begin_write(_1); _2 = em_Bag_slot(_5, 0); ember_field_begin_write(&_1->_access_items); ember_object_end_write(_1). The carried access begins before the call's whole-object write ends. Both programs pass the type checker. No test in tests/ matches `mut self) -> Span` or `mut self) -> ref mut`.

**Checker's notes.** Kind: bug, high severity. Every mut self getter is unusable at run time.

### G5-4 — A view of a class field created on only one path crashes the compiler (MIR verification ICE) — **fixed, D-455**

Kind: bug. Severity: high. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** g5-locking\q02_if_expr_two_fields.em: v = b.items[..] if len(b.log) == 1 else b.log[..] gives: thread 'main' panicked at compiler\ember_driver\src\main.rs:2322:13: MIR code-generation verification failed: em_main: bb4 receives incompatible dynamic-access states .... Also: q05 (a match choosing b.items or b.log); q01 and q03 (v: Span[int] = other[..]; if ...: v = b.items[..]; println(v)), 'bb23 ends dynamic access ... but that access is not open'; q04 (o = Some(b.items[..]) on one branch); p98 (r = b.cell.try_borrow() on a RefCell class field), 'bb5 receives incompatible dynamic-access states: previous {...}, incoming {}'. Control p99 (try_borrow on a local RefCell) prints true. Cause: insert_shared_accesses (borrows.rs:955-1028) begins an access only at created_at but places ends by NLL region membership (access_active), and a region includes join points reached on paths where the loan was never made. The same pass already ICEs on Shared payloads (q07_shared_conditional_control.em, a Shared get() chosen by if-expression). c0c7beb routed every class-field loan through it (borrows.rs:870), making the crash reachable from ordinary class code.

**Suggested fix (not applied).** Make placement path-sensitive. Compute an 'access open' forward dataflow (gen at the loan's creation, kill where it ends) and place ends only where it is open and the region is dead. At joins where it is open on some predecessors only, end it on the open edges or carry a runtime flag. Equivalently, use the borrow checker's loans-in-scope set instead of region membership.

**Checker's evidence.** q02_if_expr_two_fields.em fails with 'MIR code-generation verification failed ... em_main: bb4 receives incompatible dynamic-access states: previous {(...Field(0)...)}, incoming {(...Field(1)...)}' and 'bb23 ends dynamic access (... Control p99 (try_borrow on a local RefCell) prints 'true'. All are legal programs, and the compiler crashes on them.

**Checker's notes.** Kind: bug, an ICE that rejects legal code. It fails closed: no unsound code is emitted. I did not verify the exact borrows.rs line numbers for insert_shared_accesses.

### G5-5 — Every borrow() or borrow_mut() of a RefCell class field panics with an exclusivity violation — **fixed, D-454**

Kind: bug. Severity: high. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** g5-locking\p93_refcell_field_borrow_legal.em (one handle: with g = b.cell.borrow(): println(g)) gives: panic at p93...:10:14: exclusivity violation: write access to Holder.cell while a read access to Holder.cell is active; active read began at 10:14 (debug and release). p94 (borrow_mut in a plain method) gives 'read access to Holder.cell while a write access ... is active'. In the emitted C (p92), the guard's ember_field_begin_read(&_1->_access_cell) is followed by ember_field_begin_write(&_1->_access_cell) around _1->cell.borrow = _1->cell.borrow + 1. Cause: lower.rs:1539-1591 writes the counter, file and line through places under the class field (the comment at 1539-1542 assumes distinct fields are disjoint), and field_accesses (borrows.rs:1090-1095) maps each write to a write access on the field's word while the guard's loan (1075-1088) holds it. No test covers a RefCell field of a class.

**Why it is wrong.** VIII.3 table: calling a method on a field is a read when the method takes self (borrow and borrow_mut do), and a guard from one holds its access until the loan dies ([EXC-18]). The RefCell's own counter enforces [CELL-5] and [CELL-6] (try_borrow returns None). The bookkeeping is interior mutability, not a write to the field, so a RefCell in a class, the main reason to have one, cannot be used at all. This is a regression from per-field words.

**Suggested fix (not applied).** Do not treat RefCell (and Cell) interior bookkeeping as a field write. Map writes under a RefCell's counter fields to no access, or to a read, and give the guard's loan a read access to the class field whether it came from borrow or borrow_mut.

**Checker's evidence.** p93_refcell_field_borrow_legal.em (one handle, `with g = b.cell.borrow(): println(g)`) panics: 'p93...:10:14: exclusivity violation: write access to Holder.cell while a read access to Holder.cell is active; active read of Holder.cell began at p93...:10:14'. p94 (borrow_mut inside a plain self method) panics: 'read access to Holder.cell while a write access to Holder.cell is active ... began at 8:18'. The comment at lower.rs:1539-1542 reads 'The counter write targets field 1 while the loan is of field 0 — distinct fields are disjoint ([BRW-4])', but per-field class access words make that counter write a write to the class field. No test in tests/ that declares a RefCell field is in a file with a class.

**Checker's notes.** Kind: bug, high severity. A RefCell held in a class is unusable through borrow() and borrow_mut().

### G5-6 — A view from a virtual or interface getter read-locks every field of the object, so legal writes to other fields panic — **fixed for virtual calls, D-467**

Kind: spec-deviation. Severity: medium. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** g5-locking\p60_virtual_getter_other_field.em: virtual fn label(self) -> str returns self.name; n = p.label(); q.tags.push(2); println(n) gives: panic at p60...:18:5: exclusivity violation: write access to Person.tags while a read access to Person.tags is active; active read of Person.tags began at p60...:17:9 (release too). p61 does the same through an interface handle. The non-virtual control p62 prints 'ann [1, 2]'. The panic falsely says a read of Person.tags is active. Source: ADR-060 ('Through a virtual or interface call the caller cannot know the field, and reads every field of the receiver object'), the D-218 row, and borrows.rs:409-435 plus codegen object_begin_read (lib.rs:2411). No owner ruling covers it.

**Why it is wrong.** [EXC-19]: access state is per field, and reading one field while writing another never conflicts. [EXC-1] panics only when an access to the same field is active. [EXC-18] carries the field's access. The whole-object read makes conforming programs panic at run time, and the spec has no whole-object read for this case.

**Suggested fix (not applied).** Carry a per-slot field summary: the union over every override of the slot in the class family (the whole program is known), or a per-class accessor in the type info and dyn table that begins exactly the fields that override's summary lists. Or put the over-approximation to the owner as an ODR.

**Checker's evidence.** p60_virtual_getter_other_field.em panics: 'p60...:18:5: exclusivity violation: write access to Person.tags while a read access to Person.tags is active; active read of Person.tags began at p60...:17:9'. The getter only returned self.name. The non-virtual control p62 prints 'ann [1, 2]'. [EXC-19] says 'reading one field while writing another never conflicts', and [EXC-1] panics only when an access to the same field is active. The whole-object read comes from ADR-060 (DECISIONS.md, 'Through a virtual or interface call the caller cannot know the field, and reads every field of the receiver object') and the D-218 row. Both are agent decisions. A grep of the spec and OWNER-QUEUE.md for a whole-object read or 'every field of the receiver' finds nothing.

**Checker's notes.** Kind: spec deviation (an agent's over-approximation with no owner ruling), medium severity. The panic message also falsely says a read of Person.tags is active.

### G5-7 — A base-class view getter called on a derived-class handle is rejected with E3060 — **open, D-460**

Kind: missed-case. Severity: medium. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** g5-locking\q12_inherited_getter_min.em (open class Base with fn view(self) -> Span[int]: return self.items; class Derived(Base); d = Derived(); v = d.view(); println(v)) gives: error[E3060]: this temporary is dropped at the end of its statement while it is still borrowed ... help: bind the handle to a variable first (`c = p.child`) ... note: a handle stored in an object can be replaced ... [RC-5]. Binding to a base-typed local first (q13: b: Base = d; v = b.view()) prints [1, 2]. The upcast of the receiver makes a temporary handle that the view then borrows.

**Why it is wrong.** [LT-1] rule 1: the result borrows the receiver, and d is a local handle, so [RC-5]'s 'handle stored in an object' does not apply. ### G8-1 — Fused reversed-enumerate check treats ANY rev above an enumerate as backwards: an even number of revs makes a correct loop panic before its first turn — **fixed, D-457**

Kind: bug. Severity: medium. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** compiler/ember_typeck/src/lib.rs:21265-21272 marks an enumerate as reversed by `node.steps.iter().any(|step| matches!(step, FusedStep::Rev(_)))`. Two revs cancel each other in the index (fused_node_value, ~21621), so the items come out forwards. But the counter is still sent to the before-the-loop check (`start + n - 1 > room`, ~21274-21296), not to the forward cut-and-check. Probe e9.em: `for i, x in xs.iter().copied().enumerate(start=int.MAX - 1).rev().rev().take(2)` (xs=[1,2,3]) prints `panic at e9.em:4:5: integer overflow in `+`` before the body runs. The unfused e10.em `...rev().rev().take(2).to_array()` prints `[(9223372036854775806, 1), (9223372036854775807, 2)]` with no panic. Same for `.rev().skip(1).rev().take(1)`: e11 (fused) panics, e10 (unfused) gives `[(9223372036854775806, 1)]`. e7/e8 (rev().rev() with no take): fused panics at once; unfused gives two items and then panics at the third, as forward enumerate does (ODR-089).

**Why it is wrong.** [CTL-3b] is a lowering: the counted loop must give the items std's adapters give, and fail where they fail. Rev(Rev(E)).next is E.next, a forward enumerate. Under ODR-089 a forward enumerate panics only at the item that passes int.MAX, never early. One of the two things the author flagged for review (the check for a reversed enumerate) is wrong on this path.

**Suggested fix (not applied).** Decide direction by how many Rev steps the counter has (odd means backwards), or let an outer Rev cancel an inner one when steps are pushed. A counter with an even count should go through the forward path (fused_numbers counters/fused_pulls), which then has to handle a Rev step instead of hitting `unreachable!` at ~21368.

**Checker's evidence.** Reproduced with my own probes in review2/g8-rev-verify/. a1.em `for i, x in xs.iter().copied().enumerate(start=int.MAX - 1).rev().rev().take(2)` (xs=[1,2,3]) prints `panic at a1.em:4:5: integer overflow in `+`` before the body runs. a2.em drives the same chain by hand with `.next()` and prints `unfused (9223372036854775806, 1)`, `unfused (9223372036854775807, 2)`, `unfused done`. a3.em (fused `.rev().skip(1).rev().take(1)`) panics at a3.em:4:5, while a4.em (the same chain with `.to_array()`) prints `[(9223372036854775806, 1)]`. Cause, as the reviewer said: compiler/ember_typeck/src/lib.rs:21265-21272 sends a counter down the reversed path when `node.steps.iter().any(|step| matches!(step, FusedStep::Rev(_)))`, so any number of Revs counts as reversed, and the check before the loop (21273-21299) then tests start + n - 1 against room. **Checker's notes.** The bug is real. Kind is right (bug). Medium severity is fair: it needs an even number of revs and a start near int.MAX.

### G8-2 — Fused reversed-enumerate overflow check is gated on the loop having a turn, not on the enumerate being pulled: skip past the end, or zip with an empty side, silently skips the panic std raises — **fixed, D-457**

Kind: bug. Severity: medium. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** lib.rs:21276 `let (turns, _, _) = self.fused_last(count, outer, span);` and the condition `turns && start + n - 1 > room`. std still pulls through Enumerate.next_back when the loop gets no turn. Skip.next pulls `left` items (core.em Skip.next). Zip.next asks `a` first. Zip.next_back trims the longer side before asking the other. Probes, with xs=[1,2,3], ys=[], top=int.MAX-1:
- e1 `for i, x in xs.iter().copied().enumerate(start=top).rev().skip(3)` prints `fused loop finished, turns: 0`; e2 (the same chain with `.next()`) prints `panic at ...std/src/core.em:766:22: integer overflow in `+``.
- e3 `...enumerate(start=top).rev().zip(ys.iter().copied())` in a for prints `fused zip loop finished, turns: 0`; e4 (same chain with `.next()`) panics at core.em:766.
- e5 `...enumerate(start=top).zip(ys...).rev()`: fused prints `turns: 0`, unfused `.next()` panics.
The emitted C for e1 (target/debug/c/e1.c, around bb15-bb22) guards the panic with `_16 = _15 != 0ULL`, the count after skip.

**Why it is wrong.** The forward path follows exactly these pulls: fused_numbers/fused_pulls number 'every item they pull: those skip and step_by pass over ... one item past a zip's shorter side'. Here std's next_back is called and panics while the fused loop runs to completion.

**Suggested fix (not applied).** Gate the reversed check on 'this enumerate's next_back is called at least once': the fused_pulls `any` for that node, extended so a Rev level is followed like the others, including Zip.next_back trimming. Do not use the loop's count.

**Checker's evidence.** b1.em, fused `for i, x in xs.iter().copied().enumerate(start=int.MAX-1).rev().skip(3)`, prints `fused skip turns 0`. b2.em, the same chain with `.next()`, prints `panic at .../std/src/core.em:766:22: integer overflow in `+``: Skip pulls 3 items through Enumerate.next_back, and the first gives number + (left-1) = int.MAX+1. b3.em, fused `.enumerate(start=top).zip(empty).rev()`, prints `fused zip.rev turns 0`. b4.em, the same with `.next()`, panics at core.em:766:22, because Zip.next_back (core.em ~776-783) trims `a` down to `b`'s length with a.next_back() calls. The fused check at lib.rs:21276 is `let (turns, _, _) = self.fused_last(count, outer, span)`, and the panic condition is `turns && past` (21295). So the check depends on the loop getting a turn, not on whether the enumerate's next_back is called. The forward path's own doc (lib.rs:21243-21249) says the numbers follow every item the adapters pull (skip, step_by gap, one past zip's shorter side), so the two paths disagree.

**Checker's notes.** Reproduced exactly. The fused and unfused programs differ on whether they panic. This is a bug in the new reversed-enumerate check.

### G8-4 — A range of more than int.MAX values has no len, so take/skip/step_by/zip/enumerate.rev() over it panics unfused while the fused for loop runs

Kind: bug. Severity: low. Reviewer's confidence: medium. Checker: **confirmed**.

**Evidence.** std/src/core.em:1466 (i64 `(end - self) as int`) and the u64/usize/u128 distance_to (panic 'a range of more than int.MAX values has no length'). Take/Skip/StepBy/Zip/Enumerate.next_back all call inner.len(). Probe w1.em: the fused `for x in (0 as u64..u64.MAX).iter().take(3).rev()` prints `fused: [2, 1, 0]`, and the fused `for x in (i64.MIN..i64.MAX).iter().take(2).rev()` prints `[-9223372036854775807, -9223372036854775808]`. The unfused `(0 as u64..u64.MAX).iter().take(3).rev().to_array()` panics: `core.em:1532:13: a range of more than int.MAX values has no length`. w2.em, the i64 unfused form, panics with a different message, `core.em:1467:17: integer overflow in `-``.

**Why it is wrong.** [STD-19] says the ranges with an end 'know their length' and that take etc. run backwards over them, with no exception for wide ranges. The fused loop (which counts in usize) and the iterator protocol disagree on whether the same program panics. The i64/isize message also differs from the other widths. Part of this may be a spec gap: len returns int, so a range longer than int.MAX cannot state its length. The divergence and the two messages are implementation issues either way.

**Suggested fix (not applied).** Either have the adapters' next_back avoid len() when only a comparison is needed (e.g. compare the remaining count without going through int), or take the case to the owner: rule that such ranges are not ExactSizeIterator, or that len panics, and make the fused loop check the same way. Make the i64/isize distance_to give the same message as the other widths.

**Checker's evidence.** c1.em, fused: `for x in (0 as u64..u64.MAX).iter().take(3).rev()` gives `[2, 1, 0]`, and `(i64.MIN..i64.MAX).iter().take(2).rev()` gives `[-9223372036854775807, -9223372036854775808]`. c2.em, unfused u64 `.take(3).rev().to_array()`, panics: `core.em:1532:13: a range of more than int.MAX values has no length`. c3.em, unfused i64, panics with a different message: `core.em:1467:17: integer overflow in `-``. i64.distance_to (core.em:1466) computes `(end - self) as int` in i64; u64 (1529-1533) checks and panics explicitly. c4.em: `(0 as u64..u64.MAX).iter().len()` panics the same way. Take.next_back (core.em:704-714) calls inner.len(). [STD-19] (spec line ~4101) says ranges with an end 'know their length' with no exception for wide ranges. A grep of the docs finds no ODR or ADR on such ranges.

**Checker's notes.** The fused/unfused split and the two panic messages are real. Confidence is medium on how to class it: part is a spec gap (len returns int, so it cannot hold a range longer than int.MAX), which belongs with the owner; the split and the i64 message are implementation issues. Low severity is right.
