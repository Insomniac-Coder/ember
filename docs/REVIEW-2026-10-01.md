## ADR-088 overlap check

Scope: ADR-088 (overlap check), D-396, D-397; commit 140d027.

**What the reviewer checked.** I read commit 140d027, the current code for check_overlapping_implementations, from_generic_recipe, recipe_interface, ty_shape, walk_side, unify_sides, occurs_on_side, known_bounds_hold, interface_shown and the collect_implements collision arm (compiler/ember_typeck/src/lib.rs about lines 8093-8456 and 10105). The algorithm has not changed since the commit. I also read ODR-092, ADR-088, the D-396 and D-397 rows, [TYP-19] and [TYP-20] in Hardened_48, the three new tests and the AUDIT edit. I wrote 30 probes under scratchpad/review/g1-overlap/ and ran them only with `ember check` or `ember build --emit c`.

These cases work correctly. Overlaps are found for: generic against generic with parameters named or bounded apart; Pair[T, int] against Pair[str, U]; nested Wrap[Wrap[T]]; generic against concrete; a generic struct's, enum's or class's own `implements` against an extension or a concrete implementation; built-in generics (Array, Option); tuple, fn, fixed-array and pointer shapes nested in arguments; generic interface arguments (Conv[T] against Conv[int]); `Self`-defaulted interface arguments on user generics; blanket against concrete and blanket against generic; and generic implementations in different modules. Nothing is reported for: different interface arguments (Cv2[int] and Cv2[bool]); Conv[T] against Conv[Array[T]] (the occurs check works); different array lengths; a bound that a written type misses (String is not Copy, Gadget is not Foo). Implementations the bounds keep apart pick the right one at use (p08's C calls the concrete one for Pair[String, int] and the generic one for Pair[int, int]). Bounds met through generic extensions (Array, Box, Option, Span) and through a header `implements` are seen.

The unification itself is sound: the two sides' parameters are kept apart even when they share a name, walk_side cannot loop, and the occurs check is correct. The problems are in what gets fed to it (records that are silently dropped), in how bounds are checked, and in the instance-time safety net that the commit removed.

Not applicable: const generics are not built yet (E1010), and `From` is not declared, so [ERR-7] cannot be probed.

### G1-1 — A generic implementation whose interface cannot be resolved in the pass is silently dropped, and the instance-time E2041 is now suppressed, so the overlap reaches C as a function defined twice

Kind: bug. Severity: high. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** lib.rs:8226 `let Some(instance) = self.recipe_interface(entry, &params, owner, module) else { continue };` drops the record whenever resolving the interface reports anything (recipe_interface rolls the report back and returns None). lib.rs:8213-8216: for a BUILTIN_GENERICS target `owner` is None, so an interface argument that defaults to `Self` cannot resolve. An interface argument written as an associated type (`Conv[I.Item]`) also fails, because projection_params and current_generics are not set up for the extension. Meanwhile lib.rs:8131-8139 now emits E2041 at an instance only for (false,false); (false,true) and (true,true) fall to `_ => {}`. Probe p16b_builtin_self.em: `interface Combine[R = Self]` with `extend[T] Array[T] implements Combine` and `extend Array[int] implements Combine`, used through `use_it[C: Combine]`. `ember check` prints nothing (exit 0), and `--emit c` contains `int64_t em_Array_i64_combine(ember_vec* _1, ember_vec* _2) {` twice (lines 1080 and 1090). Probe p14b_assoc.em: `extend[I: Iterator] Wrap[I] implements Conv[I.Item]` and `extend[U] Wrap[U] implements Conv[int]`, used at Wrap[Counter] (Counter's Item is int). `check` is clean, and the C defines `em_Wrap_Counter_conv` twice (lines 1172 and 1182, returning 2 and 1). Before 140d027, collect_implements emitted E2041 for any repeated (type, interface), so both programs were rejected at the instance. This brings back D-396's 'function defined twice' symptom, now with no diagnostic at all.

**Why it is wrong.** [TYP-19] MUST: two implementations whose applicable types overlap are E2041. ADR-088 says the pass covers every generic recipe, and the instance-time check was removed on that assumption. The assumption fails for any recipe whose interface does not resolve in the pass's scope. The result is a miscompile, not merely a missing diagnostic.

**Suggested fix (not applied).** Never drop a record. For a built-in generic, resolve with the recipe's instance type built over its parameters (as user generics do through named_types). Declare projection parameters for `implements` entries the way collect_generic_extensions does for member signatures. If resolution still fails, give the record wildcard interface arguments so that it overlaps conservatively. Also keep a general backstop in collect_implements: a collision at an instance whose pair the pass did not report is still E2041. Add tests for both shapes.

**Checker's evidence.** Rewrote both shapes as my own probes. v1a_builtin_self.em (`interface Merge[R = Self]`, `extend[T] Array[T] implements Merge` + `extend Array[int] implements Merge`, used through `go[C: Merge]`): `ember check` exit 0, no output; `--emit c` has `int64_t em_Array_i64_merge(ember_vec* _1, ember_vec* _2) {` at lines 1084 and 1094. v1c_assoc.em (`extend[I: Iterator] Holder[I] implements Into2[I.Item]` + `extend[U] Holder[U] implements Into2[int]`, used at Holder[Ticker]): check exit 0; C defines `em_Holder_Ticker_into2(em_Holder_Ticker* _1) {` at lines 1172 and 1182. Control v1b (same Array pair but explicit `Merge[int]`) is reported: `error[E2041]: \`Array[i64]\` and \`Array[T]\` can be one type, and both implement \`Merge[i64]\``, so the drop is specific to records whose interface fails to resolve. Code matches the claim: lib.rs:8226 `let Some(instance) = self.recipe_interface(...) else { continue };`, recipe_interface rolls back and returns None on any report (8336-8339), owner is None for BUILTIN_GENERICS (8213-8216), and collect_implements 8129-8139 emits E2041 only for (false,false). `git show 140d027` shows the removed unconditional `format!("\`{shown}\` already implements \`{written}\`")` E2041 in collect_implements.

**Checker's notes.** Real miscompile (duplicate C definition, no diagnostic). High severity stands.

### G1-2 — known_bounds_hold checks only part of a bound, so pairs the bound keeps apart are reported as overlapping

Kind: spec-deviation. Severity: medium. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** lib.rs:8444-8449: a bound whose interface instance has generic arguments is skipped as `open` without substituting what unification made those arguments, and `param.bindings` (associated-type equalities) are never looked at. Probe p05_bounds.em X1: `extend Gadget implements Conv[bool]`, `extend[T, U: Conv[T]] Pair[T, U] implements X1`, `extend Pair[int, Gadget] implements X1` gives `error[E2041]: \`Pair[i64, Gadget]\` and \`Pair[T, U]\` can be one type, and both implement \`X1\``. Here U is Gadget, written in full, and T is int, so the bound is Conv[int], which Gadget does not meet. The same bound written concrete (`U: Conv[int]`, X2) is correctly not reported. Probe p12b_blanket.em: the blanket `extend[T, Q: Key[T]] Wrap[T] implements Get[Q]` against `extend Wrap[int] implements Get[Gadget]`, where Gadget implements no Key at all, gives E2041. Probe p28_assocbound.em: `extend[T: Iterator[Item = int]] Wrap[T] implements X` against `extend Wrap[Words] implements X`, where Words' Item is str, gives E2041. Yet p28b shows the compiler knows Words fails that bound: `error[E2040]: \`Words\`'s \`Item\` for \`std.core.Iterator\` is \`str\`, but \`T\`'s bound needs \`i64\``.

**Why it is wrong.** ODR-092 / [TYP-19]: 'A bound separates two only where the type it bounds is written out in full and does not meet it.' In each probe the bounded type is written in full and does not meet the bound as unification fixes it, so the two do not overlap. Valid programs are rejected. Note that the blanket form is exactly ODR-042's Map/Index[Q: AsKey[K]] pattern.

**Suggested fix (not applied).** Before checking, substitute the unification bindings into the bound's interface arguments. Use the existing bound-check machinery so associated-type bindings are compared too. Treat a bound as unknown only when something in it is still an open parameter after substitution.

**Checker's evidence.** v2a_bound_generic_args.em: `extend Gizmo implements Conv[bool]`, `extend[T, U: Conv[T]] Pair[T, U] implements Mark`, `extend Pair[int, Gizmo] implements Mark` -> `error[E2041]: \`Pair[i64, Gizmo]\` and \`Pair[T, U]\` can be one type, and both implement \`Mark\``; v2b with `U: Conv[int]` is accepted (exit 0). v2c_assoc_bound.em: `extend[T: Iterator[Item = int]] Holder[T] implements Mark` vs `extend Holder[Words] implements Mark` (Words' Item = str) -> E2041 `\`Holder[Words]\` and \`Holder[T]\` can be one type`. v2e_blanket_key.em: `extend[T, Q: Key[T]] Holder[T] implements Fetch[Q]` vs `extend Holder[int] implements Fetch[Gizmo]` with Gizmo implementing no Key -> E2041. Code: known_bounds_hold lib.rs:8444-8449 skips any bound whose open_interface_origin args are generic (`open`) without substituting, and never reads param bindings. Spec [TYP-19] (Hardened_48 line 1110-1118): 'A bound separates two only where the type it bounds is written out in full and does not meet it' — in each case the bounded type (Gizmo, Words, Gizmo) is written in full and fails the bound as unification fixes it.

**Checker's notes.** Valid programs rejected; spec-deviation is the right kind.

### G1-3 — A bound met only through a blanket implementation is treated as unmet, so a real overlap is missed

Kind: missed-case. Severity: medium. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** lib.rs:8449 calls `self.implements(ty, interface)`, which does not consult blankets. The checker's own `implements_or_blanket` (lib.rs:4197-4202) does, through apply_blanket. Probe p26_lazy.em X2: with `extend Gadget implements Key[int]` and `extend[T, Q: Key[T]] Wrap[T] implements Get[Q]`, the pair `extend[U: Get[Gadget]] Holder[U] implements X2` and `extend Holder[Wrap[int]] implements X2` is not reported. Wrap[int] does implement Get[Gadget]: p26b compiles `w.get(Gadget(v = 0))`. The Option and Span bounds in the same probe are reported correctly.

**Why it is wrong.** [TYP-19] MUST: Holder[Wrap[int]] is a type both implementations apply to, since the bounded type is written in full and meets the bound, so this is E2041. (At use only the concrete implementation is applied, so nothing is miscompiled; the overlap is just not diagnosed.)

**Suggested fix (not applied).** Have the bound check consult blankets as implements_or_blanket does, for example by collecting the bound questions and answering them with &mut self after unification.

**Checker's evidence.** v3a_blanket_met.em: `extend Gizmo implements Key[int]`, `extend[T, Q: Key[T]] Holder[T] implements Fetch[Q]`, `extend[U: Fetch[Gizmo]] Box[U] implements Mark`, `extend Box[Holder[int]] implements Mark`, plus `need(Holder(x = 1))` where `need[F: Fetch[Gizmo]]`: check exit 0 with no output, so Holder[int] is accepted as Fetch[Gizmo] at a call yet the Mark overlap at Box[Holder[int]] is not reported. Control v3b (`extend[T] Option[T] implements Foo`, `Box[U: Foo]` vs `Box[Option[int]]`) is reported E2041. known_bounds_hold calls `self.implements` (lib.rs:8449, &self, defined 27303) while the call-site check uses implements_or_blanket (4198-4202) which also runs extend_instance_at_use and apply_blanket.

**Checker's notes.** Missed diagnostic only; the concrete implementation wins at use, no miscompile observed.

### G1-4 — Across modules, E2041 does not show the other implementation in the human-readable output

Kind: spec-deviation. Severity: medium. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** compiler/ember_diag/src/lib.rs:294-303 keeps only labels in the primary span's file (`if label.span.file == primary_file`). Probe mods2/ (lib/shapes.em declares Wrap[T], P, Named, `extend[T] Wrap[T] implements Named` and `extend P implements Named`; main.em repeats both). The output is `error[E2041]: \`Wrap[T]\` already implements \`lib.shapes.Named\`` and `error[E2041]: \`lib.shapes.P\` already implements \`Named\``, both pointing only at lib/shapes.em with no mention of main.em. With --json the secondary label (main.em:3 and main.em:7) is present, so only the rendered text loses it. Because records are sorted by (file id, start) at lib.rs:8280, the error also lands in the imported module rather than the importing one. The messages mix qualified and unqualified names (`lib.shapes.P` vs `Named`, `Wrap[T]` vs `lib.shapes.Named`).

**Why it is wrong.** [TYP-20]: 'Two implementations of one interface for one type anywhere in a program are E2041, naming both.' ADR-088 relies on the secondary label to name the other implementation, but for implementations in different modules the rendered diagnostic names only one. Two of the commit's own messages (the same-shown 'already implements' form, and the concrete-concrete E2041) carry nothing else that identifies the other implementation.

**Suggested fix (not applied).** Render labels in other files under their own `-->` header, as rustc does. This is a general renderer fix, not one specific to E2041.

**Checker's evidence.** ember_diag/src/lib.rs:294-303 keeps a secondary label only if `label.span.file == primary_file`. My probe mods/ (lib/kinds.em declares Tagged, Cell2[T], Q and `extend[T] Cell2[T]`/`extend Q` implements Tagged; main.em repeats both): rendered output is `error[E2041]: \`lib.kinds.Q\` already implements \`Tagged\`` and `error[E2041]: \`Cell2[T]\` already implements \`lib.kinds.Tagged\``, both pointing only into lib\kinds.em; main.em is never named. `--json` carries the secondary label with file .../mods/main.em line 7 ("the first implementation is here"). Stronger case: v4b_std_collide.em (`extend int implements Default` in a user file) renders only `--> C:\Users\ism19\Code\ember\std\src\core.em:1065:23` — the user's own file and line appear nowhere in the text output.

**Checker's notes.** General renderer gap, but it defeats [TYP-20]'s 'naming both' for every cross-file collision, including user-vs-std.

### G1-5 — Instance names make `Wrap[*int]` and `Wrap[int]` one type, so E2041 reports a false overlap and the pass resolves the wrong `Self`

Kind: bug. Severity: high. Reviewer's confidence: high. Checker: **confirmed**.

**Evidence.** generic_instance_name (lib.rs:10645) builds the name from type_stem(symbol_name(arg)); `*int` renders as `*i64`, which type_stem (lib.rs:38328) reduces to `i64`, the same stem as `int`. Probe p03b_ptrname.em: `fn k(w: Wrap[int]) -> bool: return w.x` gives `error[E2020]: expected \`bool\`, found \`*i64\``, so Wrap[int] took the field type of the earlier Wrap[*int]. Probe p11_ptrcollide.em: `extend Wrap[*int] implements X` and `extend Wrap[int] implements X` give `error[E2041]: \`Wrap[*i64]\` already implements \`X\``. In the overlap pass, `owner` (lib.rs:8213-8216) is looked up by the same name, so the record for `extend[T] Wrap[*T]` is shown as `Wrap[T]` (p02_shapes A5: `\`Wrap[*i64]\` and \`Wrap[T]\` can be one type`). Interface arguments resolved through `Self` for such a recipe are also taken from the wrong instance. Other argument lists collide the same way (Pair[(int, int), int] vs Pair[int, (int, int)] both stem to Pair_i64_i64_i64).

**Why it is wrong.** [TYP-16]: each distinct instantiation is a distinct type. This collision predates the commit and is not in DEFECTS, but it makes the concrete [TYP-19] E2041 fire for two different types and feeds the wrong `Self` into the new pass.

**Suggested fix (not applied).** Make instance names injective over argument structure, for example by encoding pointer, reference, tuple and array constructors and their nesting in the stem, or by keying instances on interned argument types and keeping the name only for display and C.

**Checker's evidence.** generic_instance_name (lib.rs:10645-10648) joins type_stem(symbol_name(arg)); type_stem (38328-38339) collapses every non-alphanumeric run to '_' and trims. v5a_ptr_field.em: `fn a(w: Cell2[*int])` then `fn k(w: Cell2[int]) -> bool: return w.x` -> `error[E2020]: expected \`bool\`, found \`*i64\``. v5b_ptr_overlap.em: `extend Cell2[*int] implements Mark` and `extend Cell2[int] implements Mark` -> `error[E2041]: \`Cell2[*i64]\` already implements \`Mark\``. v5c_tuple.em: `Two[(int, int), int]` then `fn g(p: Two[int, (int, int)]) -> bool: return p.b` -> `error[E2020]: expected \`bool\`, found \`i64\`` (b should be a tuple). No DEFECTS row mentions type_stem/instance-name collision (grep -a).

**Checker's notes.** Pre-existing, not introduced by 140d027, but it feeds the new pass's owner lookup at 8215. Note 'bug' is right; it also breaks type identity outside overlap checking.

### G1-7 — A generic extension target that leaves out a defaulted type argument never matches any instance, and the overlap check skips it on argument count

### G3-1 — The closure adapters reject any callable whose value must be dropped: E3013 is reported inside std/src/core.em, not at the user's call

**Evidence.** std/src/core.em:207-208 `fn map[R, F: fn(Item) -> R](owned self, f: F) -> Map[Self, R, F]: return Map(self, f)` (the same shape for filter, filter_map, take_while, skip_while and inspect, lines 211-226) moves the borrowed parameter `f` into the struct. compiler/ember_analysis/src/drops.rs:927 allows that only when the type has nothing to drop. Probe p12b.em:

**Checker's evidence.** Probe g3-adapters-verify/p1.em (`s = "abc".to_string(); n = xs.iter().map(owned fn(x: ref int) => x + s.len()).count()`) gives `error[E3013]: cannot move out of a borrowed parameter --> C:\Users\ism19\Code\ember\std\src\core.em:208:26` (`return Map(self, f)`).
