# E5034 — a C++ construct the importer does not support

```cpp,file=shapes.hpp
#pragma once

struct Named { int id = 0; };
struct Sized { int size = 0; };

class Both : public Named, public Sized {
public:
    Both() noexcept {}
};
```

```cpp,file=facade.hpp
#pragma once

// A facade with no bases, defined in C++ beside `Both`, which stays there.
class BothFacade {
public:
    BothFacade() noexcept;
    ~BothFacade();
    int id() const noexcept;

private:
    struct Impl;
    Impl* impl_;
};
```

```ember,fails
import cpp "shapes.hpp"

fn main():
    unsafe:  # SAFETY(ffi): a constructor call
        both = cpp.Both.new()
```

## Why

Some C++ constructs cannot cross a C boundary in a way that means the same thing on every compiler.
With multiple inheritance or a virtual base, the address of a `Both` and the address of its `Sized`
part differ by an offset the C++ ABI decides — and MSVC's ABI and the Itanium ABI (GCC, Clang)
decide it differently. An Ember pointer to one would be right on one compiler and silently wrong on
the other. The importer refuses such a class instead, naming the row of `[FFI-48]`'s table that
rules it out and what to do instead.

## The fix

Keep the class in C++ behind a facade Ember can import: here one with no bases at all, whose methods
reach the `Both` it holds.

```ember,fixed
import cpp "facade.hpp"

fn main():
    unsafe:  # SAFETY(ffi): the box owns the facade for every call
        facade = cpp.BothFacade.new()
        println(facade.get().id())
```
