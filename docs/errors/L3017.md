# L3017 — reference cycle detected

```ember,fails
class Node:
    name: String
    next: Option[Node]

fn main():
    a = Node("a", None)
    b = Node("b", Some(a))
    a.next = Some(b)
```

```text
warning[L3017]: reference cycle detected
runtime ownership cycle:
  objects: Node@0000021C8A1F0D40 Node@0000021C8A1F0CA0
  strong edges: 2
  statically predicted: yes
  suggested weak edge: none
  edges:
    strong Node.next: Node@0000021C8A1F0D40 -> Node@0000021C8A1F0CA0
    strong Node.next: Node@0000021C8A1F0CA0 -> Node@0000021C8A1F0D40
  shortest cycles:
    Node.next -> Node.next: Node@0000021C8A1F0D40, Node@0000021C8A1F0CA0
```

A debug run (`ember run`, the `debug` profile) prints this when the program ends
(`[WK-15]`); `--no-leak-check` turns it off. The compiler's `L3001` already warned
that `Node.next` can close a cycle.

## Why

An object is freed when its last strong handle goes. Objects that hold strong
handles to each other keep each other's counts above zero after the program has
let go of all of them, so they are never freed (`[WK-1]`): a leak that no amount of
reading the code near the leak explains. The report names, for each leaked object,
the shortest strong cycle through it as `Type.field` edges (`[WK-4]`), which is the
list of fields to choose the weak one from.

## The fix

Make one edge of each cycle weak: a `Weak` handle does not keep its object alive,
and `upgrade` gives the object back while something else does.

```ember,fixed
class Node:
    name: String
    next: Weak[Node]

fn main():
    a = Node("a", Weak[Node].empty())
    b = Node("b", Weak(a))
    a.next = Weak(b)
```
