# E5050 — a type with no foreign representation

```ember,fails
struct Frame:
    pub items: Array[i32]

extern "C" fn submit(f: Frame) -> i32:
    return 1

fn main():
    print(1)
```

```text
error[E5050]: `Frame` has no foreign representation
 --> page.em:5:22
  |
5 | extern "C" fn submit(f: Frame) -> i32:
  |                      ^^^^^^^^ `f` is this parameter
  |
  = note: every type in an `extern` signature must be FFI-safe [FFI-5]
```

## Why

An `extern "C" fn` is a promise about *layout*, made to a compiler that will
never see your source. Both sides have to agree on the size of the value, where
each field sits inside it, and who owns anything it points at — and for a type
like this there is no agreement to be had. `Array[i32]` is a pointer, a length
and a capacity, owning a heap buffer whose allocator is Ember's. A C caller
handed that struct would have a `{ptr, len, cap}` it cannot allocate, cannot
free, and cannot grow, and one that never runs `[DRP-*]`'s drop would leak it.

`[FFI-5]` therefore restricts a foreign signature to types with a
representation the other side can state: the scalars, and `@layout(c)` structs
whose fields are themselves FFI-safe. That is a smaller set than "types with a
known size" on purpose — the question is not whether the bytes have a layout,
but whether the *contract* attached to them survives the crossing.

Note what this error is not. It is not about a type being complicated; it is
about a type carrying an obligation. A `@layout(c) struct` of four floats
crosses freely. So does a raw pointer, because a raw pointer promises nothing.

## The fix

Pass what the boundary can actually represent, and keep the Ember type on the
Ember side of it. For a container that usually means a pointer and a length —
which is what `Span[T]` already is — with the wrapper doing the conversion.

```ember,fixed
@layout(c)
struct Frame:
    pub width: i32
    pub height: i32

# A `@layout(c)` struct of scalars has a representation C can state, so it
# crosses as itself.
extern "C" fn submit(f: Frame) -> i32:
    return f.width * f.height

# A container does not. The boundary takes the pointer and the length that a
# C caller already has, and the Ember side rebuilds the view.
extern "C" fn submit_all(data: *i32, len: usize) -> i32:
    return 1

fn main():
    f = Frame(3, 4)
    print(submit(f))
```

If the foreign side genuinely needs to own an Ember value, hand it an opaque
handle rather than the value: declare the type as an `extern type` on the C
side, pass a pointer, and keep construction and destruction in Ember, where the
drop rules still hold.
