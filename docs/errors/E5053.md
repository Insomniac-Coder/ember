# E5053 — an instrumented run contradicted a declared foreign effect

```ember,fails
unsafe extern "C":
    @ffi(effects=[])
    fn malloc(size: usize) -> *mut void
    @ffi(effects=[Alloc])
    fn free(block: *mut void)

@test
fn allocates():
    unsafe:  # SAFETY(ffi): the block is freed once, by the allocator that made it
        block = malloc(16)
        free(block)

fn main():
    pass
```

```text
error[E5053]: an instrumented run contradicted `malloc`'s effects: it reached Alloc
 --> src/main.em:3:5
  |
3 |     fn malloc(size: usize) -> *mut void
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  |
  = help: add `Alloc` to its `@ffi(effects=[…])`, if the function does that
  = note: a run of `test --instrument-ffi` saw the call reach an intercepted entry point of that kind [FFI-37c]
```

`ember test --instrument-ffi` reports it, after the tests ran, and the run fails.

## Why

A foreign function's `@ffi(effects=[…])` is a promise nobody checks at
compile time: the compiler cannot see into the C library. Callers rely on it —
a `@noalloc` function may call `malloc` above only because its declaration says
it does not allocate. An instrumented test run watches the allocation, lock,
wait and I/O entry points while each foreign function runs; when it sees one
of a kind the declaration says the function never reaches, the declaration is
wrong, and every guarantee built on it is wrong with it. That is not a grade to
lower quietly: it is an error, so the declaration is fixed before anything
trusts it again.

## The fix

State the effect the function has (or stop calling it where it is not allowed):

```ember,fixed
unsafe extern "C":
    @ffi(effects=[Alloc])
    fn malloc(size: usize) -> *mut void
    @ffi(effects=[Alloc])
    fn free(block: *mut void)

@test
fn allocates():
    unsafe:  # SAFETY(ffi): the block is freed once, by the allocator that made it
        block = malloc(16)
        free(block)

fn main():
    pass
```
