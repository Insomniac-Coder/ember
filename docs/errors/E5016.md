# E5016 — an `_Atomic` C type that `Atomic[T]` is not

```c,file=levels.h
#include <stdatomic.h>
static inline float level_peek(_Atomic float* level) { return atomic_load(level); }
```

```c,file=counts.h
#include <stdatomic.h>
static inline unsigned count_peek(_Atomic unsigned* count) { return atomic_load(count); }
```

```ember,fails
import c "levels.h"

fn main():
    peek = c.level_peek
```

```text
error[E5016]: `level_peek` was not imported from `levels.h`: parameter `level`: `_Atomic(float)`: `Atomic[T]` holds an integer, a `bool` or a pointer ([THR-14])
```

## Why

C's `_Atomic T` crosses as `std.sync.Atomic[T]`, so a C function and an Ember program can share one
counter or flag, each with its own atomic operations on the same bytes. That holds only when the two
agree on what the bytes are: `Atomic[T]` is laid out as `T` and is made of the integers, `bool` and
pointers its operations are defined for. An `_Atomic` C lays out otherwise (a padded or lock-based
one, which some targets use for wide or odd-sized types), or of a type `Atomic` does not hold, would
be read and written by two different protocols; the importer leaves out what uses it and says why.

## The fix

Share an atomic of a type `Atomic[T]` holds:

```ember,fixed
from std.sync import Atomic, MemoryOrder
import c "counts.h"

fn main():
    count: Atomic[u32] = Atomic(3)
    count.store(4, MemoryOrder.Release)
    unsafe:  # SAFETY(ffi): `count` lives for the call
        println(c.count_peek(ref_to_ptr(ref mut count)))
```
