# L3013 — long-term class access held across a call

Both examples are compiled in a package whose `ember.toml` turns the lint on:

```toml
[lints]
l3013 = "warn"
```

```ember,fails
open class Counter:
    value: i32

    fn init():
        this.value = 7

    virtual fn read() -> i32:
        return this.value

    virtual fn update() -> i32:
        this.value += 1
        return this.read()

class Alternate(Counter):
    fn init():
        super.init()

    override fn read() -> i32:
        return this.value

fn main():
    alternate = Alternate()
    counter: Counter = alternate
    println(counter.update())
```

```text
warning[L3013]: long-term access to `this` is live across this call
 = help: end the access before the call, or move the call outside the mutable method
```

This is an opt-in lint: enable it with `l3013 = "warn"` in the package's
`[lints]` manifest section. The program still compiles.

## Why

An open class can be extended elsewhere, so a virtual or dynamic call made
while a mutable receiver access is live can run code that re-enters the same
class hierarchy. Keeping the access live makes an otherwise local mutation
depend on implementation choices in a callee the method cannot see. The lint
marks that review boundary before effects analysis can prove the call harmless.

## The fix

Run the virtual call after the method that changes the object has returned.
Here `bump` changes the counter and returns; `update` only reads it, so it
holds no long-term mutable access when it makes the virtual call:

```ember,fixed
open class Counter:
    value: i32

    fn init():
        this.value = 7

    virtual fn read() -> i32:
        return this.value

    fn bump():
        this.value += 1

    virtual fn update() -> i32:
        return this.read()

class Alternate(Counter):
    fn init():
        super.init()

    override fn read() -> i32:
        return this.value

fn main():
    alternate = Alternate()
    counter: Counter = alternate
    counter.bump()
    println(counter.update())
```

When mutation is necessary, split the work so the virtual or dynamic call runs
after the mutable method has returned, or pass the small value it needs rather
than the active class receiver.
