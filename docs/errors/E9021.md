# E9021 — the C++ runtime of an import could not be determined

```toml
[package]
name = "page"
version = "0.1.0"

[cpp.engine]
flags = ["@engine.rsp"]
```

```cpp,file=engine.hpp
#pragma once

inline int twice(int x) noexcept { return 2 * x; }
```

```ember,fails
import cpp "engine.hpp" with (project = "engine")

fn main():
    unsafe:  # SAFETY(ffi): a scalar call
        println(cpp.twice(2))
```

```text
error[E9021]: the C++ runtime of `engine.hpp` could not be determined: its project's flags pass the response file `engine.rsp`
 --> page.em:1:1
  |
1 | import cpp "engine.hpp" with (project = "engine")
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  |
  = help: write the project's runtime switch (`/MD`, `/MDd`, `/MT` or `/MTd`) and those defines in its `[cpp.<project>]` flags
  = note: the MSVC runtime switch, `_DEBUG` and `_ITERATOR_DEBUG_LEVEL` change the C++ standard library's layout and heap, and the build inherits them byte for byte [BLD-FFI-1b]
```

## Why

The build compiles every translation unit of the target with the C++ project's runtime switch,
`_DEBUG` and `_ITERATOR_DEBUG_LEVEL` (`[BLD-FFI-1b]`), because they decide the C runtime's heap and
the standard library's layout. A response file passes flags the importer does not read: whatever
runtime it names stays unknown, and guessing one would compile Ember's side against another
standard library than the project's. The build stops instead.

## The fix

Write the project's runtime switch, and any of the two defines it sets, in its section's flags.

```toml
[package]
name = "page"
version = "0.1.0"

[cpp.engine]
flags = ["/MD"]
```

```ember,fixed
import cpp "engine.hpp" with (project = "engine")

fn main():
    unsafe:  # SAFETY(ffi): a scalar call
        println(cpp.twice(2))
```
