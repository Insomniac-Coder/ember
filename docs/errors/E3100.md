# E3100 — an unsafe step outside an `unsafe:` block

```ember,fails
@safety("p points to four readable bytes")
unsafe fn read_u32_le(p: *u8) -> u32:
    # SAFETY: the caller promised four readable bytes at `p` (`@safety` above)
    unsafe:
        return (p.read() as u32) | ((p.add(1).read() as u32) << 8) | ((p.add(2).read() as u32) << 16) | ((p.add(3).read() as u32) << 24)

fn parse(data: Span[u8]) -> u32:
    return read_u32_le(data.as_ptr())

fn main():
    pass
```

```text
error[E3100]: `read_u32_le(data.as_ptr())` (line 8) calls an `unsafe fn`, whose callers must make true what its `@safety` says; put line 8 in an `unsafe:` block with a `# SAFETY:` note saying why that holds here: above line 8 write `# SAFETY:` and the reason, then `unsafe:`, and indent line 8 under it
```

The steps that need `unsafe` are `[UNS-1]`'s list: reading, writing or offsetting through a raw
pointer, casting between pointers or pointers and integers, calling an `unsafe fn` or a C function
whose contract is not verified, a foreign `static mut`, `transmute`, `get_unchecked`, `assume_init`,
`assume_disjoint`, and implementing an `unsafe` interface or `Send` by hand.

An `unsafe fn`'s own body is no `unsafe` context either (`[UNS-12]`): each of its unsafe steps sits in
an `unsafe:` block of its own, and one outside is this error, once for each statement:

```ember,fails
@safety("p points to four readable bytes")
unsafe fn read_u32_le(p: *u8) -> u32:
    return (p.read() as u32) | ((p.add(1).read() as u32) << 8) | ((p.add(2).read() as u32) << 16) | ((p.add(3).read() as u32) << 24)

fn main():
    pass
```

```text
error[E3100]: `read_u32_le` is an `unsafe fn`, which says its callers must vouch; the reads through `p` on line 3 are this function's own unsafe steps, and nothing says why they are sound; put line 3 in an `unsafe:` block with a `# SAFETY:` note saying why the read is safe: above line 3 write `# SAFETY:` and the reason, then `unsafe:`, and indent line 3 under it
```

## Why

Everything that can break a safety promise is possible only inside `unsafe` (`[UNS-11]`), so that a
reader, a reviewer and `ember tcb` find every place a person vouches for what the compiler cannot
check, each with its reason. `unsafe` before a declaration says its users must vouch; before a block it
says this code does. An `unsafe fn` is the first kind only: its callers vouch for what its `@safety`
says, and that does not vouch for the function's own reads, so each of those still names its reason in
a block of its own.

## The fix

Put the statement in an `unsafe:` block whose `# SAFETY:` note says why the step is sound here, after
checking that it is:

```ember,fixed
@safety("p points to four readable bytes")
unsafe fn read_u32_le(p: *u8) -> u32:
    # SAFETY: the caller promised four readable bytes at `p` (`@safety` above)
    unsafe:
        return (p.read() as u32) | ((p.add(1).read() as u32) << 8) | ((p.add(2).read() as u32) << 16) | ((p.add(3).read() as u32) << 24)

fn parse(data: Span[u8]) -> Option[u32]:
    if data.len() < 4:
        return None
    # SAFETY: the length check above guarantees four readable bytes
    unsafe:
        return Some(read_u32_le(data.as_ptr()))

fn main():
    pass
```

Where a safe operation does the same, use it instead: `get(i)` for `get_unchecked(i)`, `assert_disjoint`
for `assume_disjoint`.
