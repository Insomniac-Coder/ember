# E3100 — an unsafe step outside unsafe code

```ember,fails
@safety("p points to four readable bytes")
unsafe fn read_u32_le(p: *u8) -> u32:
    return (p.read() as u32) | ((p.add(1).read() as u32) << 8) | ((p.add(2).read() as u32) << 16) | ((p.add(3).read() as u32) << 24)

fn parse(data: Span[u8]) -> u32:
    return read_u32_le(data.as_ptr())

fn main():
    pass
```

```text
error[E3100]: `read_u32_le(data.as_ptr())` (line 6) calls an `unsafe fn`, whose callers must make true what its `@safety` says; put line 6 in an `unsafe:` block with a `# SAFETY:` note saying why that holds here: above line 6 write `# SAFETY:` and the reason, then `unsafe:`, and indent line 6 under it
```

The steps that need unsafe code are `[UNS-1]`'s list: reading, writing or offsetting through a raw
pointer, casting between pointers or pointers and integers, calling an `unsafe fn` or a C function
whose contract is not verified, a foreign `static mut`, `transmute`, `get_unchecked`, `assume_init`,
`assume_disjoint`, and implementing an `unsafe` interface or `Send` by hand. Unsafe code is the inside
of an `unsafe:` block and the body of an `unsafe fn`, which is unsafe as a whole (`[UNS-12]`).

The unsafe steps of one statement are one `E3100`, naming them together, and the block it gives to
write goes around the whole statement. In a `safe:` block inside unsafe code, which is checked as safe
code, the same step is this error too, and the message says so:

```ember,fails
@safety("p points to two writable bytes")
unsafe fn clear(p: *mut u8):
    p.write(0)
    safe:
        p.add(1).write(0)

fn main():
    pass
```

```text
error[E3100]: `p.add(1).write(0)` (line 5) is in a `safe:` block, which is checked as safe code; move it out of the `safe:` block, or put line 5 in an `unsafe:` block with a `# SAFETY:` note saying why it is sound: above line 5 write `# SAFETY:` and the reason, then `unsafe:`, and indent line 5 under it
```

## Why

Everything that can break a safety promise is possible only in unsafe code (`[UNS-11]`), so that a
reader, a reviewer and `ember tcb` find every place a person vouches for what the compiler cannot
check, each with its reason. `unsafe` before a declaration says its users must vouch, for what its
`@safety` says; before a block it says this code does, for the reason its `# SAFETY:` note gives. An
`unsafe fn` says that it is unsafe, so its whole body is unsafe code, and its callers vouch.

## The fix

Put the statement in an `unsafe:` block whose `# SAFETY:` note says why the step is sound here, after
checking that it is:

```ember,fixed
@safety("p points to four readable bytes")
unsafe fn read_u32_le(p: *u8) -> u32:
    return (p.read() as u32) | ((p.add(1).read() as u32) << 8) | ((p.add(2).read() as u32) << 16) | ((p.add(3).read() as u32) << 24)

fn parse(data: Span[u8]) -> Option[u32]:
    if data.len() < 4:
        return None
    # SAFETY: the length check above guarantees four readable bytes
    unsafe:
        return Some(read_u32_le(data.as_ptr()))

fn main():
    pass
```

Where a safe operation does the same, use it instead: `get(i)` for `get_unchecked(i)`, `assert_disjoint`
for `assume_disjoint`.
