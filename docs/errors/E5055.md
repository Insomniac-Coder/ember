# E5055 — Ember code instantiates a C++ template

```cpp,file=math.hpp
#pragma once

template <class T>
T biggest(T a, T b) noexcept { return a < b ? b : a; }
```

```ember,fails
import cpp "math.hpp"

fn widest[T](a: T, b: T) -> T:
    unsafe:  # SAFETY(ffi): a call with values
        return cpp.biggest(a, b)

fn main():
    println(widest(1, 2))
```

```text
error[E5055]: `biggest` was not imported from `math.hpp`: a C++ template: only the explicit instantiations `instantiate=[…]` lists are imported, and no Ember code, generic or not, instantiates one ([FFI-17b])
 --> page.em:5:20
  |
5 |         return cpp.biggest(a, b)
  |                    ^^^^^^^
  |
  = note: the import skipped it, and said so at the import (W5002, W5001) [FFI-20a]
```

## Why

A C++ template is not code until C++ instantiates it for particular arguments, and only a C++
compiler can do that: the body may call overloads chosen by the arguments' types, use SFINAE or
concepts, or not compile at all for some `T`. An Ember generic is checked once, for every `T` at
once, and monomorphised by Ember; it cannot hand C++ a new type to instantiate a template with
while compiling Ember code. So templates cross only as the explicit instantiations the import names
— each compiled by the project's C++ compiler, with a thunk like any other function's.

## The fix

List the instantiations the program needs in `instantiate=[…]`; each is imported under a name made
of its template-id (`biggest<int>` is `biggest_int`).

```ember,fixed
from std.ffi import c_int
import cpp "math.hpp" with (instantiate = ["biggest<int>"])

fn main():
    a: c_int = 1
    b: c_int = 2
    unsafe:  # SAFETY(ffi): a call with values
        println(cpp.biggest_int(a, b))
```
