# E5054 — a range type at a foreign boundary

```ember,fails
type Roughness = f32 in 0.0 ..= 1.0

extern "C" fn shade(r: Roughness) -> i32:
    return 1

fn main():
    print(1)
```

```text
error[E5054]: `Roughness` is a range type, so it may not cross a foreign boundary
 --> page.em:3:19
  |
3 | extern "C" fn shade(r: Roughness) -> i32:
  |                   ^^^^^^^^^^^^ `r` is this parameter
  |
  = help: declare the representation and construct with `Roughness.checked(...)` in an Ember-side wrapper
  = note: a value from foreign code enters at the representation type and becomes a range value only through a checked construction [RNG-10b]
```

## Why

This one is worth reading twice, because the obvious objection is right and
does not matter. A range type **is** representable: `[COST-3]` classes it as
not observable, it erases to its `f32`, and the C side would see exactly the
`float` it expects. Nothing about the ABI is in question.

What is in question is who checked the value. `[RNG-9]` makes range validity an
*invariant*, not a convention — "a value of a range type whose representation
does not lie in the declared range is **invalid**; producing one is undefined
behaviour". That invariant is what earns the feature its keep: `[RNG-4]` may
*assume* a range value is in range, and that assumption is what discharges a
bounds check or an overflow check downstream. By `[RNG-7]` the type is also a
niche, so an out-of-range bit pattern is neither a payload nor a discriminant.

A foreign caller has made no such promise. It has a `float`, and it can pass
`-3.0` as easily as `0.5`. If that arrived typed as `Roughness`, the compiler
would go on to optimise against a range the value does not lie in, and the
result is not a wrong number — it is undefined behaviour, in Safe Ember, caused
by code with no `unsafe` anywhere in it.

So `[RNG-10b]` closes the boundary: a range type may not appear in a foreign
signature, "nor in any aggregate transitively containing one, nor as the
pointee of any pointer passed to or returned from foreign code". An
`unsafe extern` does not discharge it either — `[TIER-1]`'s boundary lets a
programmer assert a *signature*, which is a claim about layout, not a claim
about which values will arrive.

## The fix

Declare the representation at the boundary and come back in through
`[RNG-10]`'s construction set, in an Ember-side wrapper. That is one function,
and it is the only place the check has to exist.

```ember,fixed
type Roughness = f32 in 0.0 ..= 1.0

# The boundary speaks in `f32`, which is what the other side actually has.
extern "C" fn shade_raw(r: f32) -> i32:
    return shade(Roughness.clamped(r))

# And everything inside speaks in `Roughness`, with the invariant held.
fn shade(r: Roughness) -> i32:
    v: f32 = r
    if v > 0.5:
        return 1
    return 0

fn main():
    print(shade_raw(0.25))
    print(shade_raw(9.0))
```

`clamped` is the right default here: `[RNG-3a]` makes it **total**, with no
failure mode, no `Panic` and no `RuntimeCheck`, and it lowers to two compares.
A foreign caller has no error channel to receive a `Result` on anyway, so
pulling an out-of-range input to the edge is usually what you want. Use
`Roughness.checked(r)` instead when the difference between "0.5" and "nonsense
that became 1.0" has to reach the caller — then return the failure as whatever
the foreign side reads as an error.
