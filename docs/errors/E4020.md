# E4020 — an `@simd(assert)` loop did not vectorise

```ember,fails
fn gather(xs: Span[int], idx: Span[int], mut out: MutSpan[int]):
    @simd(assert)
    for i in 0..idx.len():
        out[i] = xs[idx[i]]

fn main():
    a = [1, 2, 3]
    b = [0, 0, 0]
    gather(a, [2, 1, 0], b)
    println(b)
```

```text
error[E4020]: `@simd(assert)` loop did not vectorise: it reaches memory other than a local or a view at the loop counter plus a constant
```

## Why

`@simd` asks the compiler to put a loop in **vectorisable form** and to say in
`--emit-optimization-report` whether it did; `@simd(assert)` makes failing an
error. The form is Ember's own verdict, never the C compiler's: the trip count
is known before the loop starts; every memory access is to a local or to a view
at the loop counter plus a constant; each written view is accessed at one
offset and is proved apart from every other view; every call is to a small
function the analysis reads through; no allocation, lock, blocking, I/O,
foreign call or explicit panic; no division no vector unit does; no bounds
check left; every overflow check either removed or grouped; one exit; and every
floating-point running total declared by `@parallel(reduce=…)` or allowed by
`@fastmath`. The error names the first of these the loop fails and, for a check
that remains, the check's reason.

Here `xs[idx[i]]` reads `xs` at an index the loop counter does not determine:
each turn may read any element, which no vector load does.

## The fix

Change the loop so the failing clause holds, or drop `assert` and keep the
request: the loop then runs as written either way.

```ember,fixed
fn gather(xs: Span[int], idx: Span[int], mut out: MutSpan[int]):
    @simd
    for i in 0..idx.len():
        out[i] = xs[idx[i]]

fn main():
    a = [1, 2, 3]
    b = [0, 0, 0]
    gather(a, [2, 1, 0], b)
    println(b)
```
