# E1032 — an item has the path of a module or the name of a built-in type

```ember,file=grid.em
pub fn cells() -> int:
    return 3
```

```ember,fails
import grid

struct grid:
    n: int

fn main():
    println(grid(n = 1).n, grid.cells())
```

```text
error[E1032]: item `grid` has the path of module `grid`
 --> page.em:3:8
  |
3 | struct grid:
  |        ^^^^ an item named like a module in the same scope
  |
 ::: grid.em:1:1
  |
1 | pub fn cells() -> int:
  | - module `grid` is this file
  |
  = help: rename the item, or the module's file
  = note: every item has one path [MOD-1] [MNG-1], and the item's members and the module's items would both be `grid.<name>`
```

The same code reports an item named like a module its module imports (`import paths.grid` beside
`fn grid()`), and a type declared under a built-in type's name (`struct i32`, `enum bool`).

## Why

Every item has one path, and its symbol is made from that path (`[MNG-1]`), so two items never
share a name in the C, the object files or a backtrace. A module and an item of one name in one
scope break that: the struct `grid` here and the module `grid.em` are both `grid`, so a method `cells`
of the struct and the module's `cells` would both be `grid.cells`, one symbol for two functions, and
`grid.cells()` in the source could mean either. A type named `i32` is the same problem with a
built-in type: wherever a type is written `i32` means the built-in, and the type's methods would have
the built-in's paths. Rejecting the name where it is declared keeps every path, and every symbol,
one item's.

## The fix

Rename the item (or the module's file):

```ember,fixed
import grid

struct Grid:
    n: int

fn main():
    println(Grid(n = 1).n, grid.cells())
```

For an imported module, `import paths.grid as cells` binds another name instead.
