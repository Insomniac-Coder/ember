# E5056 — an override of a C++ virtual the trampoline does not override

```cpp,file=layer.hpp
#pragma once

class Layer {
public:
    Layer() noexcept {}
    virtual ~Layer() {}
    virtual int on_update(int step) noexcept { return step; }
    virtual int priority() const noexcept { return 0; }
    int id() const noexcept { return 1; }
};
```

```ember,file=layer_overlay.em
unsafe overlay cpp "layer.hpp":
    @ffi(trampoline, virtuals=["on_update"])
    type Layer
```

```ember,file=layer_both.em
unsafe overlay cpp "layer.hpp":
    @ffi(trampoline, virtuals=["on_update", "priority"])
    type Layer
```

```ember,fails
import cpp "layer.hpp" with (overlay = "layer_overlay.em")

class Urgent(cpp.Layer):
    override fn priority(self) -> i32:
        return 9

fn main():
    pass
```

```text
error[E5056]: `priority` overrides a C++ virtual of `Layer` that its trampoline does not override
 --> page.em:4:17
  |
4 |     override fn priority(self) -> i32:
  |                 ^^^^^^^^
  |
  = help: name it in the overlay's entry: `@ffi(trampoline, virtuals=[…, "priority"]) type Layer`
  = note: the trampoline calls Ember only for the virtuals it names [FFI-39]
```

## Why

C++ code calls a virtual through the object's C++ vtable, and the trampoline subclass the importer
writes has a slot that calls Ember only for each virtual its overlay entry names. An Ember method
replacing any other virtual would be called by Ember code and never by C++: the same object would
answer `priority()` one way in Ember and another in C++, which is exactly the kind of silent split an
override exists to prevent. The trampoline also overrides every pure virtual, so a class with one
that `virtuals` does not name cannot have a trampoline at all.

## The fix

Name the virtual in the overlay's entry, so the trampoline overrides it too:

```ember,fixed
import cpp "layer.hpp" with (overlay = "layer_both.em")

class Urgent(cpp.Layer):
    override fn priority(self) -> i32:
        return 9

fn main():
    println(Urgent().priority())
```
