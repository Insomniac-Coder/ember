# E3010 — cannot move a field out of `drop`'s `mut self`

```ember,fails
struct Inner:
    pub n: i32

    fn drop(mut self):
        println(self.n)

struct Outer:
    pub inner: Inner

    fn drop(mut self):
        x = self.inner
        println(x.n)

fn main():
    _o = Outer(Inner(1))
    println(200)
```

```text
error[E3010]: cannot move a field out of `drop`'s `mut self`
  --> page.em:12:13
   |
12 |         x = self.inner
   |             ^^^^^^^^^^ moved out here
   |
   = help: use `mem.take`, `mem.replace` or `swap` to leave a value in its place
   = note: a `drop` method's `mut self` may not move fields out [DRP-5]; the field is dropped again after `drop` returns [EXP-6]
```

## Why

A destructor runs *because* the value is dying, and the fields die right after
it returns — that second destruction is not optional. Moving a field into a new
owner inside `drop` does not cancel it: the moved value drops with its new
owner at the end of the `drop` body, then drops *again* as a field. Before this
was rejected the program above printed `1` twice for one value, silently.

This is worth its own code rather than an `E3040` because the move itself is
perfectly ordinary — the same two lines outside a `drop` body are a legal
partial move. What is wrong is the *place they happen*: inside a destructor,
the source is already scheduled for destruction and cannot be given away.

## The fix

Read the field instead of moving it:

```ember,fixed
struct Inner:
    pub n: i32

    fn drop(mut self):
        println(self.n)

struct Outer:
    pub inner: Inner

    fn drop(mut self):
        println(self.inner.n)

fn main():
    _o = Outer(Inner(1))
    println(200)
```

If the field genuinely has to leave during destruction, leave a value in its
place: `mem.take`, `mem.replace`, or `swap`.
